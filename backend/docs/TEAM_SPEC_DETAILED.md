# AGENTS.md — единый контракт команды и Codex

> Проект: **«ДВИЖ» (рабочее название)** — адаптивная веб-платформа совместных спортивных активностей для кейса Столото, финал чемпионата России по дисциплине «Программирование продуктовое».
>
> Цель: **создать воспроизводимо работающий конкурсный прототип и претендовать на максимум 98/98 баллов** по предоставленным критериям. 98 — сумма указанных в критериях максимумов, а не обещание оценки.
>
> Статус: **обязательные общие инструкции** для всех участников и агентов Codex, работающих в этом репозитории. Язык продукта, UX, документации и коммуникации — русский; код и идентификаторы — преимущественно английский.

## 1. ИСТОЧНИКИ И ЦЕЛЕВОЙ РЕЗУЛЬТАТ

Официальная основа проекта — два документа, предоставленные командой:

- **«Платформа совместных спортивных активностей. Постановка задачи»** (кейс от Столото; 9 страниц требований после титула).
- **«Критерии оценки. Продуктовая и техническая части»** (5 страниц критериев после титула).

Если PDF добавлены в репозиторий, хранить исходники в `docs/source/`. Не подменять формулировки задания собственными гипотезами. Этот `AGENTS.md` кратко закрепляет требования, достаточные для параллельной разработки, но при споре необходимо сверяться с оригиналами.

**Цель продукта:** перевести человека от «хочу заниматься, но не с кем» к конкретной совместной активности: узнать **что, где, когда, с кем, на каких условиях** и записаться либо создать свою активность.

**Не является целью:** полная социальная сеть, приложение для проведения профессиональных соревнований, игровая платформа, маркетплейс бронирования залов, спортивный трекер.

**Формат:** рабочее **адаптивное веб-приложение** с UI, бизнес-логикой, постоянным хранением данных и административным контуром. Нативное мобильное приложение не требуется и не даёт дополнительных баллов. Авторизацию можно имитировать, но нельзя имитировать последствия бизнес-действий.

**Обязательный итог:** GitVerse-репозиторий с исходным кодом; доступный экспертам по сети прототип; `README.md` с запуском и ограничениями; демонстрационные аккаунты/переключение ролей; описание ролей и сценариев; презентация и готовая последовательность живой демонстрации.

## 2. МАТРИЦА ОЦЕНКИ — 98 БАЛЛОВ

| Раздел / критерий | Максимум | Что обязаны показать |
|---|---:|---|
| 1. Презентация: ясность / выступление и ответы / демонстрация | 2 + 3 + 5 = **10** | Читаемые слайды, понятная аргументация и ограничения, сквозная демонстрация трёх ролей |
| 2. Ценность основного продукта / целостность / универсальность / дополнительные идеи | 5 + 5 + 5 + 10 = **25** | Проблема «не с кем», связный путь, любой вид спорта и уровень, полезные обоснованные улучшения |
| 3. Архитектура и модель данных / обоснование технологий и развитие | 3 + 3 = **6** | Связанные сущности, корректные роли и состояния; объяснимый масштабируемый подход без ненужной сложности |
| 4. Структура и модульность / качество кода / документация | 2 + 2 + 2 = **6** | Поддерживаемый репозиторий, аккуратный код, воспроизводимый запуск и проверка |
| 5. Шесть рабочих базовых сценариев / технические доп. возможности | 6×3 + 10 = **28** | Все ветви сценариев работают с реальными данными; улучшения завершены и интегрированы |
| 6. UX шести сценариев / общий UX и UI | 6×3 + 5 = **23** | Удобные действия и прозрачные статусы; выразительный, адаптивный, доступный интерфейс |
| **ИТОГО** | **98** | |

**Принцип максимизации:** шесть базовых сценариев одновременно дают до **18 баллов за работу + 18 баллов за UX = 36**. Дополнительные улучшения потенциально дают до **10 баллов за продуктовую ценность + 10 баллов за техническую завершённость = 20**. Следовательно, **P0 — закрыть все шесть сценариев и их UX; P1 — полноценно реализовать 1–2 отличающих продукт улучшения; P2 — второстепенный polish.**

Шкала технической проверки **каждого** из шести сценариев: 0 — нет работающего сценария; 1 — отдельные действия без результата; 2 — результат достижим, но есть неработающие ветви; **3 — весь сценарий воспроизводимо работает без ручного исправления данных командой**. Статический экран не приносит технических баллов. Не выдавать дизайн-макет за реализованную возможность.

## 3. РОЛИ, ПРАВА И ИНВАРИАНТЫ

Только **три роли**:

- `USER` — обычный пользователь: ищет события, открывает карточку, записывается, задаёт вопросы, создаёт свои события, рассматривает заявки на свои события.
- `ORGANIZATION` — представитель организации/сообщества: создаёт профиль и подаёт заявку на допуск; **только после `APPROVED`** имеет публичную страницу, публикует от имени организации события, управляет их участниками и обсуждениями.
- `ADMIN` — администратор: просматривает и ищет организации и события; одобряет/отклоняет организации с причиной отклонения; снимает события с публикации/удаляет с причиной; скрывает/удаляет отдельные сообщения. **Админ не принимает заявки участников за организатора.**

**Организатор мероприятия — не четвёртая роль.** Им может выступать `USER` или одобренная `ORGANIZATION`. Организация (долговременная сущность) и её мероприятия (отдельные активности) — разные сущности.

**Состояния организации (обязательно):** `PENDING`, `APPROVED`, `REJECTED`. Причина отказа сохраняется и показывается представителю. Решение админа изменяет серверные данные. Можно предусмотреть новую заявку после отказа, но это необязательно.

**Состояния события:** `DRAFT` (внутреннее, опционально), `PUBLISHED`, `UNPUBLISHED` (снято с публикации). В реализации допустима дополнительная мягкая отметка удаления, но нельзя терять историю решений без причины. В каталоге и доступной записи участвуют **только опубликованные** события. Если сняли публикацию, запись блокируется также при прямом запросе API и прямой ссылке; организатор и уже записавшиеся видят понятный статус.

**Режимы регистрации — ОБА обязательны в одном приложении:**

1. `OPEN`: нажатие «Присоединиться» сразу создаёт подтверждённую регистрацию `CONFIRMED`; организатор видит человека среди участников.
2. `APPROVAL`: нажатие «Подать заявку» создаёт `PENDING`; организатор явно переводит её в `CONFIRMED` или `REJECTED`; обе стороны видят результат. До подтверждения человек **не** считается участником.

**Состояния регистрации:** `PENDING`, `CONFIRMED`, `REJECTED`; при реализации отмены — `CANCELLED`, при листе ожидания — `WAITLISTED`. Все состояния сохраняются в БД и отображаются на обеих сторонах.

**Другие инварианты:**

- Не допускать дублирующие активные регистрации одного пользователя на одно событие.
- Запретить участие в неопубликованных событиях независимо от способа обращения.
- Только фактический организатор данного события может принимать/отклонять заявки на него.
- До одобрения организация не может публиковать события от своего имени; после одобрения её события публикуются **без повторного обязательного согласования админом**.
- У каждого события есть название, описание, спортивное направление, дата/время, понятное место, условия участия, организатор, режим записи.
- Спорт **не ограничен жёстким enum**: пользователь может выбрать из каталога или указать новую дисциплину, не меняя код. Например, «флорбол», «шахматы», «зарядка во дворе» — одна модель события. Нормализовать пробелы и дубликаты пользовательских названий.
- Публичное обсуждение открытого события можно читать; задать вопрос может авторизованный пользователь, даже если он не записан. Организатор может отвечать. Модерация **отдельного** комментария не удаляет всё обсуждение и событие.
- Не требовать фактического подтверждения посещения, судейства, спортивных результатов, бронирования площадок, SMS/e-mail-подтверждения или внешних сервисов Столото.
- Лимит участников, лист ожидания, повторения, карта и рекомендации — **не обязательные** функции, реализовывать только если не ставят под риск P0.

## 4. ШЕСТЬ НЕПРЕРЫВАЕМЫХ END-TO-END СЦЕНАРИЕВ (P0)

Для **каждого** сценария нужны: работающая реализация, корректный UX и воспроизводимый e2e-тест (автоматический либо документированный ручной с преднастроенными данными). Проверять из интерфейса, **без ручных правок БД**.

**S1 — пользователь создаёт событие.** Зайти как `USER A` → создать мероприятие (спорт, включая **новый, ранее неизвестный системе**; дата/время; место; условия; режим записи) → опубликовать → зайти как `USER B` → найти в каталоге и открыть карточку. Проверить сохранение и корректность полей.

**S2 — допуск организации.** Зайти как представитель `ORGANIZATION` → создать профиль и отправить заявку → увидеть `PENDING` → `ADMIN` находит заявку → демонстрируется **одобрение и отклонение** на разных подготовленных примерах, при отказе указана причина → после `APPROVED` организация публикует событие сразу → обычный пользователь видит публичную страницу организации и мероприятие. При `PENDING`/`REJECTED` публикация невозможна.

**S3 — свободная запись.** `USER B` находит `OPEN` событие → читает условия → нажимает «Присоединиться» → сразу получает `CONFIRMED` → организатор видит `USER B` в списке участников. Повторный клик не создаёт дубликат.

**S4 — участие по заявке.** `USER B` подаёт заявку в `APPROVAL` → видит `PENDING` → организатор принимает → состояние `CONFIRMED` у обоих. На другом пользователе/заявке организатор отклоняет → статус `REJECTED` у обоих. Непринятый пользователь не числится подтверждённым.

**S5 — уточнение условий.** `USER B` открывает событие, **без обязательной записи**, задаёт текстовый вопрос → организатор отвечает → оба сообщения остаются на карточке с различимым авторством. `ADMIN` способен скрыть отдельно некорректное сообщение (проверить дополнительно).

**S6 — снятие с публикации.** `ADMIN` находит опубликованное событие, просматривает организатора и обсуждение → снимает с публикации **с причиной** → событие исчезает из выдачи для записи, попытка записи по прямой ссылке/API отклоняется, организатор и уже записанные пользователи видят статус. Нельзя обходить запрет из фронтенда.

## 5. ПРОДУКТОВАЯ ИДЕЯ И ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ (P1)

**Общая гипотеза:** «ДВИЖ» помогает не просто найти мероприятие, а **найти подходящую компанию** и снизить риск, что игра не состоится из-за нехватки людей. Это единая продуктовая линия, а не случайный набор фич.

**A. Объяснимое “Мне подходит” (приоритет P1).** Пользователь выбирает предпочтительные виды спорта, уровень подготовки и комфортное время/город. Система ранжирует реальные опубликованные события по прозрачным правилам и показывает основания: «ваш вид спорта», «подходящий уровень», «удобное время», «есть места». Для защиты нужен проверяемый пример, где изменение предпочтений меняет подборку. **Не нужен LLM/необъяснимый AI**.

**B. “Собрать команду” (приоритет P1).** Создатель задаёт необязательный лимит мест; карточка показывает `подтверждено / всего`, а организатор видит заполненность. В запросном режиме **только `CONFIRMED` занимают место**, `PENDING` — нет; подтверждение и свободная регистрация должны атомарно соблюдать лимит при конкурентных запросах. Если реализуется лист ожидания, явно описать правила очереди, выхода и приглашения. Не обещать его в презентации до полной реализации.

**C. “Не нашёл — создай” (малозатратное P1).** Из пустой выдачи пользователь одним действием открывает создание события с перенесёнными фильтрами. В презентации показать связь с основной проблемой.

**Опционально P2:** карта, календарь, повторяющиеся события, отмена участия, уведомления, подписки и пр. Каждая дополнительная возможность должна иметь **пользовательскую проблему → сценарий → работающую логику → данные → проверку → объяснение ограничения**. Не делать функции только ради количества экранов. Если времени мало, выполнить целиком A+B либо только A, сохранив безупречный P0.

## 6. UX/UI — ПРАВИЛА ДЛЯ ВСЕХ ЭКРАНОВ

1. Приоритет: **простота для новичка, взрослого пользователя и человека с небольшим цифровым опытом**. Русский язык, человеческие формулировки, ясная навигация, читабельные подписи, контраст и заметные элементы управления.
2. **Mobile-first + desktop**: поддержка смартфона и компьютера; без горизонтального скролла на типовых мобильных ширинах. Проверять минимум 375 px, 768 px и 1440 px (внутренний QA-ориентир команды, не официальное требование).
3. У каждой карточки ясно отображаются **спорт, название, дата/время, место, организатор, уровень/условия, режим записи, понятный CTA**. Пользователь не должен угадывать, что происходит после нажатия.
4. Показывать реальные состояния: загрузка, пустая выдача, ошибка, успех, `PENDING`, `CONFIRMED`, `REJECTED`, `UNPUBLISHED`, отсутствие мест (если лимиты реализованы), отсутствие прав. Состояния должны объяснять следующий шаг.
5. В режиме `OPEN` кнопка: **«Присоединиться»**; в `APPROVAL`: **«Подать заявку»**; после действия — соответствующий текст статуса. Не использовать одинаковую кнопку для принципиально разных режимов.
6. Простой путь: каталог → карточка → запись, а если подходящего нет — создание собственного события. Минимизировать поля, но не скрывать обязательные условия.
7. Доступность: семантические поля и кнопки, подписи, видимый фокус, клавиатурная навигация, не полагаться только на цвет, нормальные сообщения об ошибках. Не использовать недоступные внешние изображения или платные сервисы как блокирующую часть демо.
8. Выразительная **согласованная дизайн-система**: типографика, цвета, отступы, карточки, статусы, компоненты. Анимации и украшения вторичны; не перегружать основную задачу.
9. Время хранится однозначно и показывается пользователю с понятным часовым поясом; формат даты/времени должен быть согласован фронтом и бэком. Для API использовать ISO-8601 с offset/UTC, на UI — понятный локальный формат.


- Frontend: React + TypeScript; выбор Vite/Next.js и UI-библиотеки закрепляет фронтенд-команда в `frontend/AGENTS.md` и README, **без изменения REST-контракта**.
- Backend: **Java**; baseline — Java 21, Spring Boot 3.x, Spring Validation, Spring Data JPA, PostgreSQL, Flyway, OpenAPI; версия и зависимости должны быть воспроизводимо зафиксированы. Избегать микросервисов, Kafka, Kubernetes и сложных интеграций без реальной необходимости.
- Данные: PostgreSQL в общей среде; тесты могут использовать изолированную БД/контейнер. Миграции обязательны. Не хранить общие бизнес-состояния только в `localStorage` или памяти фронтенда.
- API: REST JSON, **единый контракт `contracts/openapi.yaml` — source of truth**, его создают/утверждают **до параллельной реализации эндпоинтов**. Backend соответствует контракту; frontend использует сгенерированные типы/клиент из того же контракта либо явно синхронизированные типы.
- Безопасность прототипа: экраны входа/регистрации можно имитировать. Демонстрационные сессии **выбирают заранее подготовленного пользователя**, но **права проверяются на сервере для каждого запроса**. Клиент не может назначать себе `ADMIN`, выдавать себе `APPROVED`, подменять `organizerId` или изменять заявки чужого события. Демонстрационный режим обозначить в UI и README; не выдавать его за production-auth.
- Доставка: всё поднимается локально и развёртывается с публичной ссылкой, доступной экспертам. Бесплатные/открытые зависимости предпочтительны; ограничения внешних сервисов раскрыть в README.

### 7.2 Базовая модель данных (сохранить смысл сущностей)

- `users`: id, displayName, role, preferences (или отдельная таблица), demoAccount.
- `organizations`: id, representativeUserId, name, description, sports/interests, moderationStatus, rejectionReason, createdAt/decidedAt.
- `sports`: id, normalizedName, displayName, createdBy (опционально). **Новый спорт добавляется данными, не кодом**.
- `events`: id, title, description, sportId, startsAt, locationText, conditions, level (опционально), registrationMode, publicationStatus, unpublishReason, organizerUserId / organizerOrganizationId, capacity (опционально), createdAt.
- `registrations`: id, eventId, userId, status, requestedAt, decidedAt, decidedBy.
- `comments`: id, eventId, authorUserId, body, moderationStatus, moderationReason, createdAt.
- `notifications`/`moderation_actions` — если нужны для объяснимых статусов или истории, без обязательного overengineering.

**Инвариант владельца события:** событие создано либо обычным пользователем, либо одобренной организацией; нельзя записать несуществующего организатора или смешать оба типа. Модель (дискриминатор + FK, допустимые nullable-поля или отдельные владельцы) утверждает backend-команда, но JSON DTO обязан быть однозначным для frontend.

**Нормы хранения:** внешние ключи, индексы для событий и заявок, уникальность активной регистрации пользователя на событие, транзакции для решений о заявках и лимитов. Не смешивать DTO API с JPA entities. Причины административных действий сохраняются.

## 8. ЕДИНЫЙ API-КОНТРАКТ И ПРАВИЛА ИНТЕГРАЦИИ

**Принцип:** `contracts/openapi.yaml` утверждается до начала независимой разработки фронтенда/бэкенда. Ниже — стартовая карта API. Любое изменение маршрута, названия поля, enum или формата ошибки фиксируется **в контракте и согласуется обоими ответственными**, иначе агент не должен молча расходиться с договорённостью.

Все маршруты по умолчанию имеют префикс `/api/v1`:

| Метод и маршрут | Назначение | Кто вызывает |
|---|---|---|
| `POST /demo/session` | Выбор демонстрационного аккаунта / получение тестовой сессии | Все (только демо-режим) |
| `GET /me` | Данные текущего актёра, роль, связанные сущности | Все |
| `GET /sports?search=` | Справочник + пользовательские спортивные направления | Все |
| `GET /events` | Каталог: текст, спорт, дата, город/место, режим записи; по умолчанию опубликованные | Все |
| `GET /events/{eventId}` | Карточка, владелец, режим записи, доступные действия, публичные комментарии | Все |
| `POST /events` | Создать и опубликовать событие (выбор спорта или новое текстовое название) | USER / APPROVED ORGANIZATION |
| `GET /me/events` | Собственные мероприятия | Организатор |
| `GET /me/registrations` | Мои заявки и статусы | USER |
| `POST /events/{eventId}/registrations` | Регистрация: сервер определяет `CONFIRMED` либо `PENDING` по режиму | USER |
| `GET /events/{eventId}/registrations` | Список подтверждённых и ожидающих заявок | Организатор |
| `PATCH /events/{eventId}/registrations/{registrationId}` | Подтвердить/отклонить заявку, действие `{ "status": "CONFIRMED" \| "REJECTED" }` | Организатор |
| `GET /events/{eventId}/comments` | Обсуждение события | Все, с учётом видимости |
| `POST /events/{eventId}/comments` | Добавить вопрос/ответ | Вошедший актёр |
| `POST /organizations` | Создать профиль и отправить заявку на допуск | ORGANIZATION |
| `GET /me/organizations` | Моя организация и состояние заявки/причина | ORGANIZATION |
| `GET /organizations/{organizationId}` | Публичная карточка одобренной организации и её события | Все |
| `GET /admin/organizations` | Поиск и фильтр организаций/заявок | ADMIN |
| `POST /admin/organizations/{organizationId}/decision` | `{ "decision": "APPROVE" \| "REJECT", "reason": "..." }` | ADMIN |
| `GET /admin/events` | Поиск событий, их состояний, организаторов и обсуждений | ADMIN |
| `POST /admin/events/{eventId}/unpublish` | Снять событие с публикации с причиной | ADMIN |
| `POST /admin/comments/{commentId}/hide` | Скрыть конкретный комментарий с причиной | ADMIN |

**Важно:** для требований ТЗ нужен просмотр организаторов событий и обсуждений в админке. Можно переиспользовать общую карточку и endpoints, но администратор должен иметь доступ к скрытым для общего каталога модерационным сведениям. Экран регистрации/входа обязателен; demo/session — один возможный способ реализации.

**Минимальные соглашения для OpenAPI:**

- Идентификаторы — стабильные UUID или другой **единый согласованный формат**; не использовать разные схемы на разных экранах.
- Даты — `ISO 8601`, желательно `2026-10-20T18:00:00+07:00` во входе и UTC в хранении; возвращать однозначную временную зону.
- Роли: `USER | ORGANIZATION | ADMIN`.
- `registrationMode`: `OPEN | APPROVAL`; `registration.status`: `PENDING | CONFIRMED | REJECTED` (+ опциональные расширения только после согласования).
- `organization.status`: `PENDING | APPROVED | REJECTED`; `event.status`: `DRAFT | PUBLISHED | UNPUBLISHED` (если есть `DRAFT`).
- `GET /events` возвращает предсказуемую пагинацию: `items`, `page`, `size`, `total`; сортировка по близости даты или заданному пользовательскому фильтру.
- Единая ошибка: `{ "code": "EVENT_UNPUBLISHED", "message": "Запись недоступна: событие снято с публикации", "details": {} }`; необходимые коды: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `EVENT_UNPUBLISHED`, `ORG_NOT_APPROVED`, `REGISTRATION_ALREADY_EXISTS`, `CAPACITY_FULL` (если лимит реализован).
- Согласованные HTTP-коды `200/201/400/401/403/404/409/422` по ситуации; frontend показывает **причину для пользователя**, а не технический стек-трейс.
- На стороне backend: валидация, авторизация, транзакции, нормализация спорта, работа с состояниями. Frontend **не вычисляет окончательные права и не заменяет серверную проверку**.
- На стороне frontend: типизированные API-вызовы, loading/error/empty/success, refetch/invalidation после мутаций, показ фактических статусов из backend.

До фиксации контракта разрешены только локальные прототипы с mock-data; после фиксации — моки **не должны маскировать** неработающий API в интеграционной сборке.

**Безусловные quality gates перед статусом DONE:**

- Серверные проверки: попытка обойти RBAC, зарегистрироваться после `UNPUBLISHED`, создать мероприятие от неодобренной организации, принять чужую заявку, повторно зарегистрироваться, подтвердить участника сверх лимита (если реализован).

- Сборка, линтер/форматирование и тесты запускаются одной понятной командой/набором команд из README. Отсутствие тестов нельзя скрывать формулировкой «всё работает».
- Адаптивность, читаемость, клавиатура, контраст, прозрачность статусов проверены на реальных экранах.

**Правила кода:** читаемые имена, небольшие компоненты/сервисы, разделение UI/business/data, без бессмысленной абстракции и копипаста; комментарии только для нетривиальных решений и ограничений; параметризованные запросы/ORM; server-side validation; логирование ошибок без утечки секретов. ## 11. СЦЕНАРИЙ ДЕМО И ПРЕЗЕНТАЦИЯ

Демонстрация должна быть **одним связанным пользовательским рассказом**, а не хаотическим открытием экранов:

1. Проблема и ценность: человек хочет заниматься спортом, но у него нет компании.
2. Обычный пользователь ищет мероприятие, открывает подробности, участвует через `OPEN`.
3. Тот же пользователь подаёт заявку в `APPROVAL`; другой организатор принимает и отклоняет другую заявку.
4. Пользователь задаёт вопрос, организатор отвечает; показываем связь ролей и сохранённость сообщений.
5. Организация отправляет заявку → администратор принимает/отклоняет разные заявки → допущенная организация размещает мероприятие → посетитель видит профиль организации и событие.
6. Обычный пользователь создаёт новое событие с **пользовательским видом спорта**, второй пользователь находит его.
7. Администратор снимает мероприятие с публикации и/или скрывает некорректное сообщение; демонстрируется реальное изменение UI и запрет записи по прямой ссылке.
8. Показываем **реально реализованные** дополнительные возможности A/B и почему они повышают шанс совместного занятия.
9. Кратко: схема архитектуры, БД, тесты, ограничения прототипа и потенциал развития.

Слайды должны быть читаемыми, короткими и говорить «**проблема → решение → доказательство работы → продуктовые улучшения → архитектура → ограничения**». Не утверждать наличие реальных пользователей, подтверждённой конверсии, статистики рынка или ИИ там, где есть только гипотезы/алгоритм. Длительность выступления определяется регламентом соревнования — не придумывать её.

## 12. ПРИОРИТЕТЫ И DEFINITION OF DONE

**P2 — только после закрытия P0/P1:** карта, повторные события, подписки, дополнительные интеграции, сложная геймификация, расширенные профили.

Задача **DONE**, только если выполнены все применимые пункты:

- [ ] Реализована конкретная ценность пользователя, связанная со сценарием/баллами.
- [ ] Соответствуют API и модель данных, роли/инварианты соблюдены на сервере.
- [ ] Проверены позитивные, негативные и пограничные ветви; есть тест или ручной QA-шаг.
- [ ] UI показывает реальные состояния, ошибки и адаптивно работает.
- [ ] Обновлены контракт, README/документы/демо, если затронуты.
- [ ] Другой участник может проверить результат в общей сборке, без скрытых действий разработчика.

**STOP-THE-LINE:** если ломается любой S1–S6, общая сборка, схема БД или API-контракт — немедленно исправлять регрессию перед добавлением новых фич. Завершённый простой продукт на максимальный балл предпочтительнее эффектного набора частично работающих экранов.

6. Ничего не выдавать за завершённое, если оно работает только с маковыми данными, локальной подменой ответов, преднарисованными состояниями или требует ручной подготовки во время проверки.

---

**Девиз команды:** *Не количество функций, а завершённый путь от «хочу заняться спортом» до «я записан и знаю, с кем встречаюсь» — для каждой роли, в живой системе, с доказуемым результатом.*

# Расширение v2: спортивные роли, профиль, рейтинг соревнований и переписка

> **Статус:** дополнительные требования, сформулированные командой после исходного ТЗ. **Не обязательны по официальному кейсу.** Считать приоритетом P1/P2 после воспроизводимой работы шести сценариев. Полная система проведения профессиональных соревнований, внешняя верификация квалификаций и реалтайм-мессенджер по условиям конкурса не требуются. Эта спецификация — проектные решения и допущения, допускающие изменение через согласованный PR.

## E1. Матрица ролей и модель полномочий

| Субъект/качество | Что обозначает | Что может делать без спецназначения | Чего НЕ даёт |
|---|---|---|---|
| `USER` — системный principal | Физический пользователь | Поиск, личное событие, участие/заявка, комментарии | Доступ к чужим событиям или админке |
| `ORGANIZATION` — системный контур | Коллективный аккаунт организации/сообщества | Профиль и заявка; публикация только после допуска | Автоматический допуск; возможность управлять чужими событиями |
| `ADMIN` — системный principal | Сервисная модерация | Допуск организаций, снятие событий, модерация комментариев | Принятие заявок участников за автора |
| `ATHLETE` — спортивная роль | Спортсмен/участник | Метка профиля, участие в мероприятиях | Право самоначисления очков |
| `COACH` — спортивная роль | Тренер | Метка профиля, создание **личных** тренировок | Админские полномочия, подтверждение чужого участия |
| `REFEREE` — спортивная роль | Судья | Метка профиля; при **отдельном назначении** судейские действия конкретного соревнования | Право судить все соревнования на платформе |
| `SPORTS_ORGANIZER` — спортивная роль | Организатор мероприятий/сообществ | Метка профиля, создание **личных** событий | Обход модерации организации |

`users.sportsRoles` — множественный набор, разрешить смену ролей в профиле. Авторитетное разрешение на действие проверять через `principal`, владение конкретным `event`, `approved organization`, отдельные назначенные права. `sportsRoles` никогда не должен участвовать в простом условии «есть спортивная роль → предоставь любую системную привилегию».

Организация связана с представителем (`organization_representatives`) и имеет собственную страницу и один или несколько групповых чатов. Действие от имени организации только после `APPROVED` и при проверенной связи представителя; подтверждение/отклонение заявок принимает организатор события — пользователь или представитель допущенной организации. Если модели организации/сообщества различаются в продукте, обе должны проходить предусмотренный кейсом контур допуска для публикации от коллективного имени.

## E2. Профиль и приватность

Предлагаемая модель:

```text
UserProfile {
  userId: UUID
  nickname: string               // уникальный публичный handle, нормализованный, 3..30
  firstName?: string             // личное имя, пользователь решает публичность
  lastName?: string              // фамилия, пользователь решает публичность
  avatarUrl?: string             // ссылка на разрешённое изображение / upload
  bio?: string                   // 0..500, безопасный plain text
  sportsRoles: SportRole[]       // ATHLETE, COACH, REFEREE, SPORTS_ORGANIZER
  favouriteSportIds: UUID[]
  experienceLevel?: string
  ratingPoints: integer          // READ-ONLY, сервер вычисляет
  rank: string                   // READ-ONLY, сервер вычисляет
  ratingVerifiedCount: integer   // READ-ONLY
}
```

Минимальные правила: профиль любого пользователя открывается из карточки события/списка участников/чата; редактирование — только владельцем; авторизация из текущей сессии; запрещать client-side patch вычисляемого рейтинга. Файлы аватара: допустимые типы/размеры, лимиты; можно использовать заранее заготовленные avatars или URL с безопасным fallback. Не включать телефон/электронную почту в публичный DTO. Рекламные и пользовательские HTML-теги экранировать/очищать. Никнеймы уникальны без учёта регистра, история публичной смены ника отдельно не требуется.

UI: публичный профиль и «Мой профиль» — разные режимы, наличие/отсутствие аватара, даты, ранга, bio, спортивных ролей; в профиле рейтинг объясняется через подтверждённые участия; скрывать защищённые данные; отлаженные loading/error/empty.

## E3. Соревнования и рейтинг v1

Это **дополнительная** модель. `eventKind = ACTIVITY | COMPETITION`; обе разновидности используют существующие `events`, `registrations`, комментарии и модерацию. Обычная тренировка/шахматная встреча НЕ требует результата/посещаемости. У `COMPETITION` после завершения может быть добавлена верификация фактического участия, **не влияющая на базовую запись**.

**Бизнес-событие:** `Registration CONFIRMED` → `CompetitionParticipation PENDING_VERIFICATION` → уполномоченный организатор соревнования (или специально назначенный `EventStaff(role=REFEREE)`) проверяет факт присутствия → `VERIFIED` → атомарное начисление в `rating_ledger` → новый `ratingPoints/rank` виден в профиле. Статус `NO_SHOW` очков не даёт. `REJECTED`, `PENDING`, `CANCELLED`, снятое с публикации мероприятие не должны автоматически давать баллы.

**Договор для демонстрационного MVP (можно пересмотреть обеими командами до разработки):** `+10` баллов за одно подтверждённое участие в завершённом соревновании без оценки результата или сложности дисциплины; `0` за обычную встречу или заявку. Пороговые ранги из конфигурации, пример: `0–29` «Новичок», `30–79` «Участник», `80–159` «Активный», `160+` «Легенда». Это **внутриплатформенный показатель активности**, не официальная квалификация, спортивный разряд или рейтинг результативности. Отображать правила в UI и README. Если нужна система веса/наград за разные типы соревнований, согласовать отдельную спецификацию и ограничения антинакрутки.

**Модель данных:** `competition_participations` (eventId, userId, registrationId, status, verifiedBy, verifiedAt), `event_staff` (eventId, userId, staffRole, assignedBy), `rating_ledger` (id, userId, participationId, delta, reason, verifiedBy, idempotencyKey, createdAt), `rank_thresholds`/конфигурация. Уникальный `participationId` для первоначального начисления; корректировки отдельно с referential linkage; начисление + смена статуса участия в транзакции; `ratingPoints = SUM(ledger.delta)`, rank по thresholds, история доступна пользователю/читателю по политикам приватности.

**Риски/границы:** нельзя начислять за самозаявление или событие, созданное ради накрутки, без проверки полномочий. Если проверка подлинности реального участия вне прототипа недоступна, прямо назвать это ограничением конкурса. Отмена/снятие уже подтверждённого соревнования требует явно документированной политики отзыва очков; рекомендованный вариант — запись компенсации в ledger с audit reason и ролью инициатора. `ADMIN` не получает автоматически право вмешиваться в произвольную историю без такого аудита.

**E2E проверки:** (1) у пользователя 0 баллов; (2) запись `CONFIRMED` в соревнование сама рейтинг не меняет; (3) назначенный организатор верифицирует после завершения → +10, rank корректен; (4) повторная верификация не удваивает очки; (5) другой пользователь/неуполномоченный судья получает 403; (6) обычная встреча не начисляет; (7) старый профиль после повторного запроса показывает новые данные; (8) конкурентные запросы не дают двойной `ledger`.

## E4. Приватные диалоги и беседы сообществ

**Три несовместимые по смыслу коммуникационные сущности** (не объединять под одну кнопку и одну таблицу без различимого типа и политик):

1. `event_comments` — публичное текстовое обсуждение карточки конкретного события. Это P0 по ТЗ; участвовать может авторизованный пользователь **без записи**. Админ может скрыть некорректный комментарий, не уничтожая остальные.
2. `conversations(type=DIRECT)` — личная переписка ровно 2 пользователей. Доступ к чтению/отправке только членам, каноническая пара уникальна, история постранично, отправитель из сессии. Никнеймы, аватары и ссылка на профиль. Режим реального времени не обязателен.
3. `conversations(type=COMMUNITY)` — групповая беседа одобренной организации/сообщества. Сообщество ведёт список членства, членство даёт право чтения и отправки, организатор/уполномоченный модератор управляет составом. Неавторизованные участники не видят содержимое и метаданные закрытой беседы.

**Модель:** `conversations(id,type,organization_id?,created_at,...)`; `conversation_members(conversation_id,user_id,status,joined_at,...)`; `chat_messages(id,conversation_id,sender_user_id,body,created_at,deleted_at?)`; `community_members(organization_id,user_id,status,joined_at)`; возможная `user_blocks` как P2. Индексы (conversation_id,created_at), уникальность прямого диалога по упорядоченной паре пользователей (предпочтительно через `direct_conversation_key`), ограничения на тип разговора и происхождение организации. Беседа сообщества может быть создана только в контуре одобренной организации, включая действие её представителя.

**Правила:** чужая беседа → 403/404 без выдачи текста; участник, вышедший или исключённый из закрытого сообщества, не читает **новые** сообщения (для MVP проще запрещать весь доступ после выхода; закрепить в контракте); нельзя подменять `senderUserId` или роль клиента; удаление/жалобы/блокировки — только если реализованы полноценные политики. Содержимое личных чатов не открывается администратору **по умолчанию**; модерация приватного контента требует отдельной согласованной политики репорта и аудита. `avatarUrl/bio/chatMessage` должны быть безопасно обработаны на фронтенде. Показанные статусы отправки соответствуют серверному подтверждению, а не только оптимистичному UI.

**MVP коммуникаций:** открыть/найти Direct, отправить текст, увидеть его у обоих; создать беседу одобренного сообщества, принять члена, отправить и прочитать групповой текст, исключить/выйти и проверить запрет доступа; пагинация, пустой список и обработка ошибок. Для демонстрации достаточно поллинга/обновления страницы, если это честно описано; WebSocket не нужен ради баллов сам по себе.

**E2E проверки:** Direct A↔B, повторное открытие возвращает тот же чат; C не читает по чужому UUID; B не меняет автора сообщения; разрешённый член читает и пишет в Community; неучастник не читает; после выхода нет доступа; отклонённая организация не создаёт публично действующий community-chat; публичные event_comments продолжают работать независимо.

## E5. Предлагаемые дополнительные API-контракты

Сначала оформить OpenAPI, потом писать Java и React. Пример согласуемого набора (`/api/v1`):

```text
GET   /users/{id}
GET   /me/profile
PATCH /me/profile            // только nickname, displayName, avatarUrl, bio, sportsRoles, favourites
GET   /users/{id}/rating-history
POST  /competitions/{eventId}/participations/{participantId}/verify
GET   /conversations?type=DIRECT|COMMUNITY&page=0&size=20
POST  /conversations          // DIRECT: targetUserId; COMMUNITY: approved organizationId
GET   /conversations/{id}/messages?page=0&size=30
POST  /conversations/{id}/messages   // body; sender из сессии
GET   /communities/{id}/members
POST  /communities/{id}/members     // участие по правилам членства
DELETE /communities/{id}/members/me // выход
```

DTO и коды ошибок зафиксировать в `contracts/openapi.yaml`, уточнить правила отображения авторов и статусов, ограничения длины текста, лимиты запросов, поля `ratingPoints` и `rank` read-only, `page`/`size` пагинацию. Названия endpoint в документе — **проект**, не финальная API-истина до PR. Не начинать реализацию на несовместимых догадках двух команд.

## E6. Вехи реализации и максимизация оценки

- **Release 0 (обязательно):** вся шестёрка S1–S6 с проверкой UX/серверных полномочий, демо-аккаунтами и развёртыванием. Команда может получить за это до 36 баллов из 98, остальные критерии учитывать параллельно.
- **Release 1 (ценное связное улучшение):** объяснимая персонализация + сбор команды или **одна** полностью готовая цепочка из нового набора, со сценариями и тестами. Оценка дополнительных возможностей максимум 10 продуктовых + 10 технических баллов **совокупно**, не за каждую фичу.
- **Release 2 (сообщество):** редактируемый профиль со спортивными ролями, прямые сообщения и групповой чат с membership/security.
- **Release 3 (репутация):** соревнования как подвид события + верификация посещения + рейтинг ledger + отображение ранга/истории; защищённые тесты и честное описание ограничений.

Если короткие сроки — сократить новый набор, **не вырезая ни одной обязательной ветви S1–S6**. На защите прямо отделять работающий модуль, макет и будущее. Документация, демо-данные, сценарии, тесты и ссылки — часть готовности, а не необязательный финальный штрих.
