# Технические решения и уточнения

## Поддержка · 20.10.2026

По запросу владельца продукта реализованы личная техническая поддержка, жалобы на комментарии и предложения площадок. Это дополнительная фича; исходные S1–S6 остаются доступны. Обращения читают автор и ADMIN, жалоба сохраняет приватную цитату и не выполняет автоматическую модерацию. Ответы/статусы доставляются через существующий колокольчик. [Модель, права и API](support.md).

Изучены оба PDF: `source/case-brief.pdf` — постановка задачи, `source/scoring-criteria.pdf` — критерии оценки. Они требуют шесть серверных сценариев, постоянное хранение и межролевую проверку. Официальный кейс допускает имитацию входа. Добавлены исходная командная спецификация и корневой AGENTS.md из предоставленных файлов. Подготавливается backend; UI, презентация и размещение на внешнем сервере требуют отдельной работы.

Новая структура проекта создана в отдельном каталоге, исходные файлы пользователя не изменялись. Передачи изменений в GitVerse не было. Общий контракт скопирован без правок.

## ADR-001. Модульный монолит

Java 21 и Spring Boot 3.5.16 в соответствии с baseline 3.x; PostgreSQL 17, Spring Data JPA/EntityManager, Flyway. Один процесс и одна БД. HTTP-контроллеры передают DTO в сервисы; сервисы проверяют права и выполняют транзакции; Store использует параметризованный JPQL. Отдельные entity не сериализуются. Нет внешних интеграций или платных зависимостей.

Store намеренно небольшой: его JPQL-фрагменты заданы в коде, значения приходят параметрами. Каталог фильтруется и пагинируется в БД. Для рейтинга применяется журнал, а не изменяемое клиентом поле users.rating.

## ADR-002. API и расхождения примеров

Предоставленный `contracts/openapi.yaml` определяет 51 операцию. Используются его актуальные `joinMode`, `GET /session`, `POST /events/{eventId}/registrations/{registrationId}/decision`, `/organizations/{id}/memberships` и английские ранги. В Markdown прежние `registrationMode`, `/me`, PATCH решения и `/communities/...` названы предварительными примерами; они не добавлялись как альтернативные маршруты.

Размеры полей также взяты из OpenAPI: nickname 3–40, bio до 1000. Корневые документы называют пределы и русские подписи рангов предложением; используемые сервером значения задокументированы в README.

**Неисправленная неоднозначность исходного контракта для ревью frontend/backend:** описание POST `/conversations` явно требует вернуть существующий DIRECT с HTTP 200, но раздел `responses` содержит только успешный 201. Реализация следует описанию: 201 при создании, 200 при повторном открытии. Сам YAML оставлен без изменений. Минимальная предлагаемая правка контракта — добавить response 200 со схемой Conversation. Frontend должен принимать обе ветки; это требуется подтвердить при совместном ревью, прежде чем считать черновик окончательным.

Управление исключением другого члена и NO_SHOW упомянуты в расширенной концепции, но маршрутов для них в OpenAPI нет. Реализованы предусмотренные контрактом свободное вступление и самостоятельный выход; новые публичные endpoints не изобретались.

## ADR-003. Организатор и роли

У события ровно один владелец: organizer_user_id XOR organizer_organization_id, проверяется SQL CHECK. Организацию в v1 представляет её создатель; это серверная связь, а не клиентский флаг. Коллективная публикация требует APPROVED. Роль ORGANIZATION вычисляется по допущенным организациям текущего пользователя. ADMIN не даёт права решать чужие заявки и читать чужую приватную переписку. Спортивные роли не повышают системные права.

## ADR-004. Конкурентные изменения

Все регистрации, принятие заявок, отмена, обработка очереди, редактирование лимита, модерация события и верификация сначала блокируют строку events через PESSIMISTIC_WRITE. Прочитанное число CONFIRMED и его изменение выполняются в одной транзакции. Уникальны (event_id,user_id) и idempotency_key проводки рейтинга.

Возвращение после CANCELLED использует ту же регистрацию с новым updatedAt. Очередь упорядочена по updatedAt ASC, id ASC; это время последнего вступления в очередь. При наличии очереди изменение лимита запрещено, чтобы не оставлять свободное место без перевода ожидающих. APPROVAL не имеет отдельной очереди: PENDING не резервирует место; при заполнении организатор получает EVENT_FULL.

Для DIRECT упорядочиваются UUID двух пользователей; обе строки блокируются всегда в одинаковом порядке, после чего ищется канонический direct_key. Это исключает дубли бесед. Отправка в COMMUNITY и выход сериализуются через строку организации; доступ проверяется на текущем членстве.

## ADR-005. Снятие публикации

UNPUBLISHED убирает событие из каталога и блокирует запись, решения о принятии и верификацию рейтинга. Регистрации сохраняются. Карточка доступна автору, ADMIN и любому пользователю, у которого есть сохранённая регистрация, включая CANCELLED/REJECTED: он видел это событие ранее и может узнать причину. Для остальных — 404. Восстанавливать UNPUBLISHED через `/publish` нельзя, этот маршрут обслуживает только DRAFT.

Ранее начисленные баллы остаются историческим результатом подтверждённого участия. Снятие публикации не означает автоматического признания посещения фиктивным. Исправления и компенсации потребуют отдельного контрактного API и аудита; сейчас прямого изменения журнала нет. Эта политика выбрана явно, автоматического отзыва в поставке нет.

## ADR-006. Рейтинг

+10 за одно CONFIRMED-участие в завершённом COMPETITION, не раньше endsAt. Для создания COMPETITION endsAt обязателен. Только владелец события либо назначенный EventStaff судья вправе проверять участие; спортивная роль REFEREE нужна для назначения, но сама по себе не даёт доступа. Проверять собственное участие нельзя. Повторный запрос возвращает ту же проводку. Статус Participation и Ledger записываются в одной транзакции.

Ранги и пороги: ROOKIE <30, ACTIVE >=30, EXPERIENCED >=80, ELITE >=160. Пороговые значения и очки задаются в application.yml. Внешнего доказательства фактического посещения прототип не получает — доверяет уполномоченному проверяющему.

## ADR-007. Рекомендации и время

Все timestamps хранятся как Instant, SQL timestamp with time zone, JSON — ISO 8601. Даты на входе должны содержать часовой пояс. Фильтры каталога соединены AND, вторичная сортировка id ASC.

Рекомендации v1: FAVORITE_SPORT +50, SUITABLE_LEVEL +20 (ANY либо точное совпадение уровня предпочтения соответствующего спорта), PREFERRED_TIME +20, AVAILABLE_SPOTS +10. Уровень другого спорта не используется. Время профиля ANY подходит всегда; неуказанное время баллов не добавляет. Поскольку часовой пояс профиля отсутствует в контракте, используется UTC: MORNING 06:00–11:59, DAY 12:00–17:59, EVENING 18:00–05:59. UTC указать рядом с выбором времени на frontend; для локальных городских интервалов нужно согласовать timezone-поле. City фильтруется, только если передан параметр. Равные оценки сортируются по startsAt ASC, id ASC.

## ADR-008. Демоавторизация и чаты

Демовход разрешён только при явном app.demo-enabled. Идентификатор пользователя хранится в серверной HttpSession; cookie HttpOnly, SameSite=Lax. CSRF проверяет Spring Security; исключены только POST `/demo/session` и POST `/demo/accounts`. Предыдущая сессия этого браузера инвалидируется после успешного входа или регистрации. Регистрации по паролю контракт не содержит.

Только текущие ACTIVE-члены видят COMMUNITY, включая метаданные и всю историю. После выхода закрывается вся история. Повторное свободное вступление возвращает доступ ко всей истории. Представитель организации также использует членство; он может выйти и вступить обратно. Администратору не предоставляется обход приватности. Сообщения возвращаются newest first; frontend выбирает отображение в хронологическом порядке. Обычные HTTP-запросы и polling, без WebSocket.

## ADR-009. Регистрация нового демопользователя

В ветке `feature/demo-registration-20261019` добавлен POST `/demo/accounts`: запрос содержит только nickname и displayName; ответ 201 использует существующий Session. Это реализация задачи пользователя по backend-регистрации, сформированной после аудита исходного ТЗ. OpenAPI, Java DTO, runtime-схемы и generated-типы frontend обновляются вместе. Форма frontend остаётся отдельной задачей.

Регистрация создаёт отдельную строку users в транзакции; сессия устанавливается только после успешного сохранения. Никнейм обрезается по краям и сравнивается без учёта регистра, включая конкурентные запросы через уникальный индекс normalized_nickname. Типы JSON-полей проверяются без преобразования чисел/boolean в строки. Служебные поля пользователь не передаёт.

UUID, рейтинг и начальные права назначаются сервером. Стабильный demoAccount `signup-<UUID>` не зависит от nickname; GET `/demo/accounts` возвращает также новые аккаунты без прежнего лимита 100. Выбран прежний непагинированный формат для совместимости текущего демо-интерфейса. Это решение для демонстрационного стенда; пароль, подтверждение личности и приватный способ повторного входа не вводились.

## 20.10.2026 — Личные уведомления и доставка причин модерации

По прямому согласованию владельца продукта реализован колокольчик с лентой за 30 дней. Причины снятия публикации и скрытия комментария перенесены в личные уведомления организатора/автора; на странице события и в карточке администратора их нет. Участники получают изменение статуса без чужой причины. `Event.moderationReason` deprecated, всегда null; сохранён аудит и выполнен перенос существующих причин в V5. Дополнительно согласованы статусы заявок/очереди/организации, публикация, изменение времени/места, упоминания и серверное напоминание в течение часа до старта. См.
