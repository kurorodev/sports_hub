## 1. Продукт и матрица 98 баллов

**Базовая ценность:** «хочу заниматься, но не с кем» → спорт → доступное мероприятие → понятные условия/участники → запись → обсуждение. Одинаково для разных дисциплин и уровней; пользователь может создать событие, одобренная организация — опубликовать своё.

**Дополнительная концепция команды:** спортивный профиль (фото, ник/имя, био, несколько специализаций), проверяемая история соревновательных участий и ранг, личные сообщения, групповые беседы организаций/сообществ. Это **сверх обязательного кейса**, не повод заменить создание и запись на мероприятия. Базовое ТЗ **не требует** судейства, трекера результатов, профессионального турнирного комплекса или полноценной соцсети.

## 2. Две независимые оси ролей

**Системные роли по ТЗ (права/RBAC):** `USER` — любое личное событие, поиск, запись, вопросы, управление **своими** заявками организатора; `ORGANIZATION` — коллективный субъект с допуском `APPROVED`, собственными событиями и страницей; `ADMIN` — рассмотрение/отказ организаций с причиной, модерация событий/комментариев, но **не** заявок участников. Представитель организации действует от её имени только после одобрения. Организатор **события** — владелец-`USER` либо одобренная организация, это не отдельная системная роль.

**Спортивные специализации пользователя (выбираются в профиле):** `ATHLETE` — спортсмен; `COACH` — тренер; `REFEREE` — судья соревнований; `SPORTS_ORGANIZER` — организатор соревнований/сообществ. **Несколько одновременно** (`sportsRoles[]`), не отдельные логины и не системные права. `REFEREE` ≠ `ADMIN`, `SPORTS_ORGANIZER` ≠ автоматически допущенная организация. Любой `USER` вправе создать личное мероприятие независимо от спортивной специализации. Дополнительные права судьи только при серверном назначении на **конкретное соревнование**.

## 3. P0 — неизменяемые бизнес-правила

- Организация: `PENDING | APPROVED | REJECTED`; отказ с причиной. До допуска коллективная публикация запрещена; после — без повторной обязательной премодерации события.
- Событие: `PUBLISHED | UNPUBLISHED` (опц. `DRAFT`); снятие с публикации с причиной, запись запрещена **также через API/прямую ссылку**, автор и записанные понимают причину.
- `registrationMode: OPEN | APPROVAL`; `OPEN` → сразу `CONFIRMED`, `APPROVAL` → `PENDING` → автор события принимает `CONFIRMED` или отклоняет `REJECTED`. До одобрения участник не считается подтверждённым. Доп. `CANCELLED/WAITLISTED` только если полноценны.
- Событие: название, описание, спорт, дата/время, место, организатор и переход к нему, условия/уровень/инвентарь при необходимости, режим. Новый спорт вводится **без правки кода**, каталог хранится в данных, не enum.
- Исключить дубли регистраций, подмену владельца/роли, принятие чужих заявок, публикацию от недопущенной организации, превышение лимита (если он есть). Права и транзакции — **только на backend**.
- `event_comments` — обязательное обсуждение **на странице события**, пользователь пишет **даже без записи**, автор отвечает, админ скрывает отдельный комментарий. Личные/group-чаты его **не заменяют**.
- Админ: поиск/просмотр организаций и событий, переходы на организатора, обсуждение и события организации; решения влияют на данные, а не только UI.

## 4. Шесть обязательных сценариев (S1–S6)

1. **S1:** `USER A` публикует событие с **новым видом спорта**, временем, местом, условиями и режимом; `USER B` находит/открывает.
2. **S2:** организация подаёт заявку → `PENDING`; админ демонстрирует **одобрение и отказ с причиной** на разных примерах; одобренная организация без премодерации публикует событие, пользователь видит страницу/событие; до одобрения запрет.
3. **S3:** прочитать условия `OPEN` → присоединиться → `CONFIRMED` у пользователя и участник в списке автора; нет дубликата.
4. **S4:** заявка `APPROVAL` → `PENDING` → организатор подтверждает **одну** и отклоняет **другую**, состояния видны всем сторонам; ожидающие не участники.
5. **S5:** незаписанный пользователь задаёт вопрос под событием → организатор отвечает, сообщения с авторством сохранены; админ скрывает одно некорректное сообщение.
6. **S6:** админ с причиной снимает событие → нет доступной записи в выдаче и по прямому API, статус виден автору и ранее записанным.

Обязательна реальная межролевая проверка каждого S без ручной правки БД, обе ветви решений и негативные проверки запретов.

## 5. Новые модули — обязательный общий договор, но НЕ P0 ТЗ

**Профиль:** `nickname/displayName`, `firstName?`, `lastName?`, `avatarUrl?`, `bio?`, `sportsRoles[]`, любимые виды спорта, уровень, `ratingPoints` и `rank` **только для чтения**, история подтверждённых участий. Профиль другого пользователя доступен из событий/участников/диалогов; изменение только владельцем, безопасный fallback для фото; не раскрывать контакты/личную переписку. Не считать спортивную специализацию источником серверных прав.

**Рейтинг:** `eventKind = ACTIVITY | COMPETITION` (по умолчанию `ACTIVITY`); только **подтверждённое фактическое участие в соревновании**, не заявка или простая запись, даёт баллы. Организатор конкретного соревнования или **назначенный на это событие** судья верифицирует; никто не начисляет сам себе через профиль. `rating_ledger` с уникальным источником, проверяющим и reason; повторная верификация **не дублирует** очки; коррекции — отдельные проводки. `ratingPoints` считается сервером, `rank` — по согласованным порогам, показать правила в UI/README. **Предлагаемый простой MVP:** +10 за подтверждённое участие, ранги по порогам 0/30/80/160 (детали в спецификации; согласовать до кодинга). Это **внутренний рейтинг активности**, не официальный разряд/спортивное мастерство.

**Сообщения:** три разные сущности: `event_comments` (P0, публичное обсуждение события); `DIRECT` (приватный диалог двух пользователей, только им доступен); `COMMUNITY` (беседа сообщества/допущенной организации, только текущим участникам). Доступ/отправителя проверяет сервер по сессии и членству; третье лицо не читает чужой диалог; нельзя создавать дубли диалога пары. Чаты: список, пагинация истории, отправка/чтение текста, автор/время, правила вступления/выхода и модерации, пустые/ошибочные состояния. WebSocket **не обязателен**; поллинг допускается. По умолчанию даже админ не получает доступ ко всем личным сообщениям.

**Не выдавать за готовое**, пока нет полного потока: профиль → изменение → другой пользователь видит; соревнование → подтверждение → `ledger` → новый ранг; direct/group → отправка → чтение под другим аккаунтом → запрет постороннему. Детали DTO, антинакрутки, членства, безопасности и тестов — в `docs/TEAM_SPEC_DETAILED.md`.

## 6. Дополнительные 20 баллов: стратегия реализации

Сначала **P0**, затем 1–2 полностью законченных улучшения с историей «проблема → сценарий → данные/права → UI → позитивные и негативные тесты». Кандидаты: объяснимая подборка «Мне подходит» (спорт, время, уровень, свободные места); «Собрать команду» (лимит и транзакционное заполнение только `CONFIRMED`); «Не нашёл — создай» (перенос фильтров); расширенные профиль, личные/групповые беседы, соревнования/рейтинг. Профиль и коммуникации проще закрыть целиком, чем рейтинг с верификацией, поэтому **сверять приоритеты со сроками**. Частичная геймификация, статичные чаты, фиктивные баллы не считаются готовыми. Профессиональный турнирный комплекс, судейство и AI не обязательны.

## 7. Технический контракт React ↔ Java ↔ PostgreSQL

Три слоя: React + TypeScript (frontend) → REST JSON `/api/v1` (Java 21 / Spring Boot 3.x, Bean Validation, JPA, Flyway) → PostgreSQL. Модульный монолит, JUnit/integration и e2e Playwright; без необоснованных микросервисов и платных зависимостей. БД — источник данных; сервер — источник прав/статусов/рейтинга.

```text
sports_hub/
├── README.md
├── .github/workflows/backend.yml
└── backend/
    ├── AGENTS.md
    ├── README.md
    ├── .env.example
    ├── pom.xml
    ├── src/
    ├── contracts/openapi.yaml
    ├── docs/TEAM_GUIDE.md
    ├── docs/TEAM_SPEC_DETAILED.md
    ├── docs/source/
    ├── scripts/
    ├── compose.yaml
    └── compose.local.yaml
```

Сущности P0: `users`, `organizations`, `sports`, `events`, `event_registrations`, `event_comments`, `moderation_actions`; расширения: `user_sport_roles`, `competition_participations`, `event_staff`, `rating_ledger`, `conversations`, `conversation_members`, `community_members`, `chat_messages`. FK, уникальность, индексы, миграции, UTC, транзакции; DTO ≠ JPA entities.

**API P0 (уточнить в OpenAPI):** `POST /demo/session`, `GET /me`, `GET /sports`; `GET/POST /events`, `GET /events/{id}`, `GET /me/events`, `GET /me/registrations`; `POST/GET /events/{id}/registrations`, `PATCH /events/{id}/registrations/{id}`, `GET/POST /events/{id}/comments`; `POST /organizations`, `GET /me/organizations`, `GET /organizations/{id}`; `GET /admin/organizations`, `POST /admin/organizations/{id}/decision`, `GET /admin/events`, `POST /admin/events/{id}/unpublish`, `POST /admin/comments/{id}/hide`.

**API расширений:** `GET /users/{id}`, `GET/PATCH /me/profile`, `GET /users/{id}/rating-history`, `POST /competitions/{eventId}/participations/{id}/verify`, `GET/POST /conversations`, `GET/POST /conversations/{id}/messages`, `GET/POST /communities/{id}/members` (конкретные DTO/маршруты **сначала** в OpenAPI).

UUID, JSON, ISO 8601, пагинация `{items,page,size,total}`, согласованные enum/коды ошибок и HTTP-статусы. Ошибка: `{ "code":"FORBIDDEN", "message":"Нет доступа", "details":{} }`. Нельзя доверять `role`, `userId`, `verifiedBy`, `ratingPoints` из тела клиентского запроса. API и модели не менять молча в одной команде.

## 8. UX/UI — 23 балла

Русский mobile-first (375/768/1440 px), доступная типографика, контраст и клавиатура, ясные CTA, loading/empty/error/success; минимум шагов каталог → карточка → участие. `OPEN` → «Вы участвуете», `APPROVAL` → «Ожидает» / «Принято» / «Отклонено»; показать причину административных решений. Основная карточка — условия, спорт, место/время, организатор, режим. Профиль с фото/рангом и «Сообщения» — отдельные удобные разделы; **публичные комментарии события не спрятать в приватных чатах**. Клиент всегда показывает серверное состояние, не начисляет рейтинг и не повышает роли.

## 9. Проверки, сдача и Definition of Done

**Seed:** несколько `USER`, `ADMIN`, организации `PENDING/APPROVED/REJECTED`, разный спорт и оба режима записи, участники/заявки `PENDING/CONFIRMED/REJECTED`, вопрос/ответ. Для расширений — пользователь с несколькими спортивными ролями, соревнование с подтверждённым и неподтверждённым участием, DM и групповой чат; только вымышленные данные.

**Тестировать:** S1–S6 и все ответвления; запреты неопубликованного события, чужой заявки, неодобренной организации, дубликатов, скрытия отдельного комментария; лимиты в конкурирующих запросах (если есть). Для P1 — запрет подмены профиля/самоначисления/двойного начисления, смена ранга после верификации, чтение чужого DM/чата неучастником (403/404), исключение из сообщества, история/пагинация. Java integration + UI/e2e; честно фиксировать неавтоматизированные проверки.

**DONE =** работающие данные и права на сервере + позитивные и негативные тесты + UX всех статусов + обновлённые API/миграции/README + независимое воспроизведение другим разработчиком. Не делать неподкреплённых заявлений «проверено».

**Сдача:** GitVerse, доступный экспертам по сети веб-прототип, README с зависимостями, командами запуска, demo-account, seed и S1–S6/P1, ограничениями и внешними сервисами, презентация. Демонстрация: сначала шесть P0 со сменой системной роли и реальными переходами статусов, затем **только работающие** улучшения (профиль/чат/рейтинг при их готовности). Разделять реализованное, макет и планы.
