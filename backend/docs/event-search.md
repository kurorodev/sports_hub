# Поиск мероприятий

Каталог использует прежний `GET /api/v1/events?q=…`: название, описание и пользовательское название активности. Контракт не меняется. Регистр и разница `е`/`ё` не влияют на совпадение; буквальная подстрока продолжает работать (`пит` → `Чаепитие`). `%` и `_` во вводе считаются обычными символами.

Для слов длиной 5–24 символа допускается одна неверная, пропущенная, лишняя буква либо перестановка соседних букв: `чаипитие`, `чаептие`, `чаепиитие`, `чаеиптие` находят `Чаепитие`. Короткие фрагменты ищутся точно, чтобы ограничить случайные совпадения. В запросе из нескольких слов каждое слово должно найтись хотя бы в одном из полей, порядок слов не важен. Опечатки не исправляют содержимое поля и сохранённые данные.

Реализация: `EventTextSearch` строит параметризованные `LIKE`-шаблоны с одним изменением. Фильтрация выполняется в БД до подсчёта общего количества и пагинации, совместно с городом, датами, статусом и прочими фильтрами. Миграции и новые зависимости не нужны; используются переносимые JPQL-функции. Правила повторены в `frontend/src/mocks/event-search.ts`.

Чтобы ограничить размер SQL, нечёткий поиск применяется к запросам до 64 символов и четырёх слов из букв/цифр. Более длинный ввод и запросы с пунктуацией ищутся как буквальная подстрока. Это базовый допуск одной опечатки, без синонимов, исправления раскладки и смыслового поиска. Сортировка остаётся выбранной пользователем.

Ручная проверка: создать опубликованное будущее событие «Чаепитие», проверить `пит`, `чаипитие`, `чаептие`, `чаепиитие`, `чаепитие`, затем неподходящий город и отсутствие совпадений. Проверить те же варианты в mock mode. Автоматические тесты и сборка для этого изменения не запускались по просьбе пользователя; выполнение на Java/PostgreSQL пока не подтверждено.
