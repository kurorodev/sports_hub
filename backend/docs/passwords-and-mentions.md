# Пароли и упоминания

Обновление 19.10.2026 в ветке `frontend`. Обычная регистрация интерфейса теперь создаёт аккаунт с паролем. Старые демоаккаунты сохранены; пароль им автоматически не назначается. Изменены общий OpenAPI, runtime-схемы и generated-типы клиента. После объединения с каталогом спорта миграция V4 добавляет хеш пароля и таблицы упоминаний без удаления пользователей, событий и сообщений.

## Вход

- `POST /api/v1/auth/register`: `{nickname, displayName, password}` → 201/Session.
- `POST /api/v1/auth/login`: `{nickname, password}` → 200/Session.
- `DELETE /api/v1/auth/session`: cookie + `X-CSRF-Token` → 204.

Регистрация и вход работают при `DEMO_ENABLED=false` и не требуют прежнего CSRF. Никнейм принимается с одним `@` или без; в БД хранится без `@`, уникален без учёта регистра. Для новых аккаунтов и изменения никнейма: 3–40 латинских букв, цифр, `_` или `-`. Имя в профиле: 1–100 символов. Пароль: 8–128 символов, не пробельный; пробелы по краям значимы и не удаляются.

Пароли хеширует Spring Security: PBKDF2-HMAC-SHA256, случайная соль 16 байт, 310000 итераций, ключ 256 бит, формат `{pbkdf2}…`. Реализация основана на [официальном PasswordEncoder](https://docs.spring.io/spring-security/reference/6.5/features/authentication/password-storage.html). Хеш не включён в публичные DTO, списки или Session. Аккаунт с паролем не имеет `demoAccount`; список и метод демо-входа дополнительно исключают такие записи. Старый `POST /demo/accounts` сохранён для совместимости и только деморежима; `/register` его больше не использует.

Успешный вход заменяет только текущую сессию, выдаёт новую HttpOnly-cookie и CSRF. Неуспешный вход/регистрация сохраняет прежнюю сессию. Неверный пароль и неизвестный пользователь дают одинаковые 401; для неизвестного пользователя также выполняется проверка хеша. Конфликт никнейма — 409, некорректные данные — 400. Сервер ограничивает суммарно регистрацию/вход до 60 запросов в минуту на IP экземпляра: 429 и `Retry-After: 60`. Используется адрес соединения, входящим forwarded-заголовкам лимитер не доверяет. Лимитер хранит до 10000 минутных окон в памяти; для нескольких экземпляров понадобится общий лимитер.

Сессии остаются в памяти backend: после его перезапуска нужно войти заново, пользователь и хеш сохраняются в PostgreSQL. Смена никнейма не меняет пароль. Смена/восстановление пароля и назначение пароля старому демоаккаунту пока не реализованы. Для HTTPS-развёртывания нужны `COOKIE_SECURE=true` и существующая настройка общего origin/CORS; текущий стенд остаётся локальным.

## Упоминания

`GET /api/v1/users?nicknamePrefix=ath` возвращает до 8 `PublicUser`, отсортированных по никнейму; допустим ведущий `@`, длина префикса без него 1–40. Endpoint не выдаёт хеши или служебные идентификаторы входа.

В обсуждении встречи ввод `@` и начала никнейма открывает подсказки. Выбор мышью или стрелками/Enter вставляет `@nickname`; Escape закрывает подсказки. Отправка остаётся явной кнопкой. Если подсказки недоступны, никнейм можно написать вручную.

Backend определяет известные упоминания при сохранении комментария или сообщения DIRECT/COMMUNITY. В `Comment` и `Message` добавлено необязательное поле `mentions`: массив `{userId, nickname, start, end}`. `start/end` — UTF-16 offsets в сохранённом тексте, `end` не включается; `nickname` — снимок текста после `@`. ID и диапазоны назначает сервер, клиент передаёт прежний `{text}`. Email и неизвестные никнеймы остаются текстом. Привязка сохраняется в `comment_mentions`/`message_mentions`, поэтому переименование или последующая регистрация прежнего никнейма не перенаправляет старые ссылки другому человеку. У старых сообщений массив пустой.

Frontend отображает проверенные диапазоны как ссылки `/users/{userId}`, остальное — обычным текстом; HTML не исполняется. Скрытый комментарий не раскрывает текст или упоминания в публичном интерфейсе. Упоминание не добавляет человека в закрытую беседу и не даёт ему права чтения. Уведомления об упоминаниях не добавлялись. Интерфейс личных/групповых бесед не создавался в этой задаче; их существующий API возвращает те же метаданные.

Mock mode эмулирует поток отдельно: хеши через Web Crypto PBKDF2, без паролей в открытом виде в localStorage. Это средство локальной демонстрации, не замена серверной аутентификации. Real mode проверяет пароль только на backend.

## Проверки

`mvn verify`: 51 тест; `mvn -Ppostgres-it verify`: 90 суммарно (39 PostgreSQL), без ошибок и пропусков. Отдельная тестовая PostgreSQL создаётся Testcontainers, рабочая БД не очищается. Контракт: 62 операции, ресурсы и generated-типы синхронизированы. Frontend: 267 unit/RTL, 67 mock browser, 25 Java browser-сценариев (4 новых + 21 регрессии); детали и история исправлений тестовых ожиданий — в [QA.md](../../frontend/docs/QA.md).

При объединении веток 20.10.2026 номер миграции паролей изменён с V3 на V4: V3 занят уже применённым справочником спорта. Для БД, где применена V3 из прежней ветки `frontend`, перед обновлением требуется согласовать историю Flyway; автоматический reset/repair не выполняется.
