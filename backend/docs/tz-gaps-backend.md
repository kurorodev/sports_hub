## Готовность трёх серверных зависимостей

| Функция | Действующий API | Статус |
|---|---|---|
| Публичный профиль организатора | `GET /api/v1/users/{userId}` | Реализован ранее, доступен гостю |

Исходное ТЗ допускает имитацию регистрации и входа. Здесь выбран работающий поток создания отдельного пользователя в PostgreSQL без пароля. Существующие демоаккаунты не переименовываются и не используются вместо нового пользователя. Экран регистрации остаётся задачей frontend.

## Действующий контракт регистрации

`POST /api/v1/demo/accounts`, только при `DEMO_ENABLED=true`. Новый метод описан в [OpenAPI](../contracts/openapi.yaml), runtime-схемах и generated-типах frontend.

```json
{
  "nickname": "novice-runner",
  "displayName": "Новый участник"
}
```

- `nickname`: строка 3–40 символов после `strip()`, уникальная без учёта регистра.
- `displayName`: строка 1–100 символов после `strip()`.
- Пустые/пробельные значения, числа, boolean и лишние поля отклоняются.
- UUID, системные права, рейтинг и `demoAccount` назначает сервер.

| Статус | Ответ | Значение |
|---|---|---|
| 201 | Существующий DTO `Session` | Пользователь сохранён, сессия установлена |
| 400 | `ApiError`, `VALIDATION_ERROR` | Некорректный запрос |
| 409 | `ApiError`, `CONFLICT` | Никнейм занят, включая конкурентный запрос/другой регистр |
| 404 | `ApiError`, `NOT_FOUND` | Деморежим выключен |

Успешный ответ устанавливает HttpOnly-cookie `SPORT_SESSION` и содержит `csrfToken`. Bootstrap-запрос регистрации не требует CSRF. Последующие бизнес-запросы требуют `credentials: include` и `X-CSRF-Token`. Неуспешная регистрация не меняет существующую сессию. Повтор успешно выполненного запроса даёт 409, а не вход в существующий аккаунт; отдельной идемпотентности сетевых повторов нет.

## Хранение, права и повторный вход

Новый пользователь имеет только USER, нулевой рейтинг, пустые спортивные специализации и предпочтения. Его создание завершается в транзакции до установки сессии. Конкурентные регистрации защищены существующим уникальным индексом `normalized_nickname`; новые миграции не понадобились.

Серверный `demoAccount` имеет вид `signup-<UUID>` и не меняется при смене nickname. `GET /demo/accounts` возвращает все демоаккаунты, включая новые; прежнее скрытое ограничение 100 элементов снято без изменения формата массива. Для повторного входа frontend передаёт `DemoAccount.id` как `accountId` в существующий `POST /demo/session`.

Регистрация, как и вход, заменяет только сессию текущего браузера. Другие сессии продолжают работать. Системные роли или допуск организации нельзя передать телом запроса. Пользователь хранится в PostgreSQL; сессии остаются в памяти приложения. Созданные аккаунты доступны общему механизму демопереключения, поэтому это не парольная авторизация и не подтверждение личности.

## Что остаётся frontend

Можно подключать профиль организатора, показывать `requirements` и добавлять экран регистрации к действующему API. После 201 отменить старые запросы, очистить приватный кэш, сохранить Session/CSRF как при текущем переключении аккаунта. `SPORT_SESSION` из JavaScript не читать. Обработать 400/409/404 и сохранить разрешённый контекст возврата.

Нужно провести приёмку самих новых экранов после их реализации; текущая backend-проверка не означает готовности этих экранов. Карта и уже работающие S1–S6 сохраняются.
