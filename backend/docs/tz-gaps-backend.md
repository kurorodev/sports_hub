# Задачи backend по результатам проверки исходного ТЗ

Дата: 19.10.2026. Проверенная версия: `641a763`.

Основание: [аудит](tz-audit-2026-10-19.md), [постановка задачи](source/case-brief.pdf). Связанные задачи: [frontend](../../frontend/docs/TZ_GAPS_FRONTEND.md).

## Что уже реализовано

| Функция | Подтверждение | Нужна ли новая backend-функциональность |
|---|---|---|
| Публичный профиль пользователя | `ProfileController`: `GET /api/v1/users/{userId}` → `UserProfile`; чтение гостем разрешено в `SecurityConfig` | Нет |
| Чтение и изменение собственного профиля | `GET/PATCH /api/v1/me/profile`, изменение только текущего пользователя | Нет; изменение профиля не заменяет создание нового аккаунта |
| Условия участия | `Api.EventCreate`, `Api.EventPatch`, `Api.Event`; `EventService.create/patch`, `Views.event`; поле `events.requirements` | Нет |
| Демо-вход | `GET /api/v1/demo/accounts`, `POST/DELETE /api/v1/demo/session`, `GET /api/v1/session` | Нет для входа в уже существующие аккаунты |
| Регистрация нового пользователя | Ни в OpenAPI, ни в контроллерах/сервисах создания аккаунта нет; `SessionService.login` только ищет существующий `demoAccount` | Да, если реализуется предлагаемый ниже поток создания нового демопользователя |

Исходное ТЗ требует показать экраны регистрации и входа и разрешает имитацию. Оно не обязывает вводить парольную авторизацию или новый endpoint регистрации. Для чисто демонстрационного экрана без создания аккаунта backend можно не расширять; UI обязан честно объяснять результат. Этот документ предлагает более полный вариант: минимальное создание пользователя в демонстрационной БД, затем существующая cookie-сессия.

## Предложение нового контракта — ещё не реализовано

Сначала согласовать с frontend и обновить `contracts/openapi.yaml`. Следующее описание является проектом, а не действующим API.

### Метод

`POST /api/v1/demo/accounts`

Путь дополняет существующий `GET /api/v1/demo/accounts`. Доступен только при `DEMO_ENABLED=true`, аналогично остальным demo-операциям. Обозначение `demo` сохраняется намеренно: здесь нет пароля и подтверждения личности.

Предлагаемый запрос `DemoRegistrationRequest`:

```json
{
  "nickname": "novice-runner",
  "displayName": "Новый участник"
}
```

- `nickname`: обязательный текст, 3–40 символов после обрезки пробелов, уникальный без учёта регистра; та же нормализация, что при изменении профиля.
- `displayName`: обязательный текст, 1–100 символов после обрезки пробелов.
- `additionalProperties: false`.
- Идентификаторы, системные права, рейтинг и служебные поля назначаются сервером.

Предлагаемый успех: **201 Created**, существующий DTO `Session`, новая HttpOnly-cookie `SPORT_SESSION`. Допустимо передать `Location: /api/v1/users/{userId}`. Формат `Session` не менять ради этой операции.

Предлагаемые ошибки в существующем формате `ApiError`:

| Статус | Код | Ситуация |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Некорректные, пустые или лишние поля |
| 409 | `CONFLICT` | Нормализованный nickname уже занят |
| 404 | `NOT_FOUND` | Деморежим выключен |

Не вводить новый код ошибки без необходимости. Для ошибки поля, если применяется, использовать текущий массив `details` с `field: "nickname"`.

## Реализация backend после согласования

1. Добавить DTO и сервис создания пользователя. Создавать нового `UserEntity` в транзакции, с новым UUID и `admin=false`.
2. Обрезать и проверить поля после нормализации. Пустая строка после `strip()` должна давать 400.
3. Использовать существующие уникальные ограничения `users.nickname`, `users.normalized_nickname`. Одновременная регистрация одинакового nickname должна давать один 201 и один 409, а не 500 или два пользователя.
4. Рейтинг нового пользователя — нулевой, спортивные специализации/предпочтения пустые; системная роль только USER. Допуск организации остаётся отдельным уже существующим процессом.
5. Назначить серверный стабильный уникальный `demoAccount`, например `signup-<UUID>`, длиной не больше 80. Не связывать его изменяемость со сменой nickname.
6. Согласовать повторный демо-вход: новый пользователь должен быть доступен через `GET /demo/accounts` и существующий `POST /demo/session`. Учесть текущий лимит 100 элементов в `SessionService.accounts()`: не оставлять созданные аккаунты недоступными для повторного выбора после достижения этого лимита. Если для решения потребуется менять DTO/пагинацию, сначала согласовать это отдельно в OpenAPI.
7. Создание строки завершать транзакционно; выдачу сессии выполнять только для успешно созданного пользователя.
8. Переиспользовать общую логику установления сессии из `SessionController.login`: инвалидировать прежнюю сессию этого браузера, сохранить новый security context через `HttpSessionSecurityContextRepository`, выдать и сохранить CSRF-токен. Не инвалидировать сессии других пользователей/браузеров.
9. Разрешить гостевой POST именно на новый demo-метод. Предлагаемое правило bootstrap/CSRF — такое же точечное исключение, как у `POST /demo/session`. Остальные POST/PATCH/DELETE продолжают требовать CSRF. Нельзя отключать CSRF для всего `/api/v1`.
10. При выключенном деморежиме отклонять запрос до создания пользователя. Не изменять готовые аккаунты seed и не превращать регистрацию в `PATCH /me/profile` выбранного демопользователя.
11. Держать contract resources согласованными: `contracts/openapi.yaml`, `src/main/resources/static/openapi.yaml`, `api-schemas.json`, Java DTO. Новая операция должна проходить `scripts/check_contract.py`.

Для профиля и `requirements` текущих таблиц достаточно. Для предложенной регистрации обязательная новая таблица не требуется: необходимые поля и уникальные индексы уже есть. Изменение миграций допустимо только при фактической потребности реализации; старые применённые миграции не редактировать.

## Проверки

Добавить API/integration-проверки:

- Гость создаёт нового пользователя → получает 201/Session → `GET /session` возвращает того же пользователя.
- Созданный пользователь читается через публичный `GET /users/{id}` и после восстановления сессии остаётся тем же пользователем.
- Новый CSRF-токен подходит для нескольких последовательных бизнес-запросов, включая создание личного события.
- Повторный demo-вход после выхода возможен по согласованному механизму; изменения профиля не ломают стабильный `demoAccount`.
- Некорректные длины, пробельные значения и лишние поля дают 400. Подмена `admin`, `systemRoles`, `id`, `ratingPoints`, `demoAccount` отклоняется.
- Занятый nickname, вариант другого регистра и конкурентная регистрация проверены на PostgreSQL; нет дублей и 500.
- `DEMO_ENABLED=false` → 404, пользователь не создаётся.
- После смены сессии старый CSRF не подходит. Действующая бизнес-авторизация S1–S6 сохранена.
- Существующие `requirements` по-прежнему сохраняются и возвращаются, а публичные профили читаются без входа.

```sh
# Из backend/
python3 scripts/check_contract.py
mvn verify
mvn -Ppostgres-it verify
```

Добавить новый сценарий в README и серверный smoke/QA, затем вместе с frontend проверить: регистрация → создание события → другой пользователь видит событие и профиль → условия участия отображаются. Перезапуск сервера не должен удалять созданного пользователя из PostgreSQL; потеря сессии при перезапуске в текущей модели допускается и должна оставаться задокументированной.

## Порядок совместной работы

1. Frontend может сразу делать страницу профиля и вывод/ввод `requirements` на существующем контракте.
2. Согласовать минимальную demo-регистрацию и её OpenAPI. Реальная парольная авторизация в эту задачу не входит.
3. Backend реализует согласованный метод и проверки; frontend генерирует типы и подключает экран.
4. Провести совместную приёмку трёх пробелов и регрессию S1–S6. Обновить документацию по фактически реализованному результату.

Создание этого файла не меняет API, базу, авторизацию или работающий стенд.
