# Демонстрация backend

Запустить сервер с деморежимом по README. Для автоматического API-прогона: `python3 scripts/smoke.py`. Для ручных запросов удобно импортировать contracts/openapi.yaml в API-клиент; хранить cookies раздельно для каждой роли и передавать X-CSRF-Token из текущей сессии. Этот документ описывает серверную проверку. Основные S1–S6 уже интегрированы с frontend; новый UI регистрации подключается отдельно.

1. **S1.** Войти `coach`, создать OPEN-событие с `sport: {customName: "Флорбол"}`, будущим startsAt, location, organizer USER с собственным id. Под `athlete-a` найти его через `/events?sport=Флорбол`, открыть карточку. Указание нового спорта создаёт строку в каталоге.
2. **S2.** Под `org-pending` получить `/me/organizations`, выбрать PENDING. Попробовать создать событие от его имени — 403 ORGANIZATION_NOT_APPROVED. Под `admin` найти заявку через `/admin/organizations?status=PENDING`, одобрить POST decision APPROVE. Представитель после этого создаёт событие без новой премодерации. Под другой ролью проверить страницу организации и её события. Для отказа создать вторую организацию через POST /organizations и передать REJECT с reason: организация видит REJECTED и причину. Не изменять БД вручную.
3. **S3.** `athlete-a` открывает OPEN, читает условия и POST registrations `{}`. Ответ CONFIRMED; под автором GET participants содержит пользователя. Повторный POST — 409 ALREADY_REGISTERED.
4. **S4.** `athlete-a` и `athlete-b` подают заявки на APPROVAL. Обе PENDING и отсутствуют в participants. `coach` подтверждает первую и отклоняет вторую через POST registrations/{id}/decision. Обе стороны перечитывают статусы. `admin` при попытке принять заявку получает 403.
5. **S5.** Незарегистрированный пользователь пишет POST comments `{text:"Можно новичку?"}`, `coach` отвечает. Чтение публично, авторы различимы. `admin` скрывает один комментарий с причиной: пользовательский список больше его не содержит, остальная ветка остаётся. В GET /admin/comments скрытая запись остаётся для проверки.
6. **S6.** `admin` вызывает POST unpublish с reason. Событие исчезает из каталога, POST registrations по прежнему UUID получает 409 EVENT_NOT_AVAILABLE. Автор и ранее зарегистрированный получают карточку UNPUBLISHED с moderationReason; посторонний — 404.
7. **Команда.** Заполнить OPEN с maxParticipants=2, третьему участнику добавить waitlist. Отменить одного подтверждённого — первый ожидающий становится CONFIRMED, число занятых мест остаётся 2.
8. **Профиль и подборка.** PATCH /me/profile задаёт sportsRoles, sportsPreferences и preferredTime. Другой пользователь получает новый профиль GET /users/{id}. GET /events/recommended возвращает score/matchReasons; смена предпочтений меняет основания. PATCH ratingPoints/rank/системных ролей запрещён.
9. **Рейтинг.** Под `athlete-b` GET /users/{id}/rating показывает 20. Найти завершённое «Соревнование №3» через `/events?includePast=true&eventKind=COMPETITION` и его CONFIRMED-регистрацию под `coach` (GET registrations). `referee` вызывает verify; профиль получает 30, ACTIVE. Повтор возвращает ту же ledger.id и 30. Посторонний, включая администратора, получает 403. Простой выбор REFEREE в профиле не заменяет назначение на событие.
10. **Переписка.** A создаёт DIRECT с peerUserId B, пишет текст; B видит его и ответом создания получает тот же чат с HTTP 200. C и администратор не читают чужой чат. Одобренный представитель создаёт COMMUNITY; другой пользователь вступает POST memberships, читает/пишет, выходит DELETE memberships/me. После выхода список и история недоступны.

Демоданные изменяются реальными запросами и сохраняются. После прохождения шагов 2 и 9 первоначальные статусы уже изменены: для повторной демонстрации допуска создайте новые организации, в рейтинге повторный verify показывает идемпотентность без новых очков. Автоматический smoke использует свои новые события и организации.

## Регистрация нового демопользователя

POST `/demo/accounts` с новым `nickname` и `displayName` возвращает 201/Session и cookie. Проверить GET `/session`, PATCH `/me/profile` с новым CSRF и создание личной встречи. Другим аккаунтом открыть профиль и событие; повторная регистрация того же nickname в другом регистре — 409. Получить стабильный `DemoAccount.id` из GET `/demo/accounts`, выйти и повторно войти через POST `/demo/session`. Не подменять новую регистрацию изменением seed-аккаунта. Это демонстрационная регистрация без пароля.
