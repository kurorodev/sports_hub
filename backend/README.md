# Стечение — backend

Поиск мероприятий: [подстроки, небольшие опечатки и ограничения](docs/event-search.md).

Фильтры комментариев в админке: [выбор автора/мероприятия, последние 10 и последние 24 часа](docs/admin-comment-filters.md).

Техническая поддержка: [обращения, жалобы, предложения площадок и приватная переписка](docs/support.md). Контракт включает 73 операции; миграции V6–V8 добавляют обращения, историю, точку и связь с опубликованной площадкой.

Бэкенд платформы совместных спортивных активностей по предоставленным PDF, командной спецификации и OpenAPI. Java 21, Spring Boot 3.5.16, Spring Security, Spring Data JPA, PostgreSQL, Flyway, Maven. Реализованы 73 операции актуального контракта: шесть обязательных сценариев, регистрация демопользователей, API профилей, рекомендаций, очереди ожидания, рейтинга, переписки и карты.

Это серверная часть общего репозитория; frontend находится в [../frontend](../frontend/). Экран `/register` создаёт аккаунты с паролем; `/login` принимает никнейм с `@` или без. Демо-вход сохранён для прежних аккаунтов. Статус проверок и ограничения приведены ниже и в [docs/verification.md](docs/verification.md).

## Быстрый запуск через Docker

Блоки с `cd backend` запускаются из корня репозитория; остальные команды — из `backend/`.

Нужны Docker Engine и Docker Compose v2 с доступом к Docker Hub и Maven Central при первой сборке.

Если JDK, Maven и Compose уже установлены, одна команда выполняет сборку с тестами, поднимает PostgreSQL и backend, ожидает готовности API и запускает HTTP smoke:

```bash
cd backend
bash scripts/start-local.sh
```

Запускайте её из обычного терминала. Maven собирает JAR один раз на компьютере; Compose использует `compose.local.yaml` и `Dockerfile.runtime`, которые упаковывают готовый JAR без загрузки Maven-зависимостей в Docker. Для повторного запуска уже собранного приложения без изменений кода: `bash scripts/start-local.sh --skip-build`. Если Docker доступен только с правами администратора, скрипт вызовет `sudo` только для Docker-команд. Результаты сохраняются в `build-latest.log`, `startup.log`, `smoke-latest.log`; при ошибке готовности/HTTP-проверки — также в `startup-diagnostics.log`.

Для Debian 13 подготовлен установщик JDK 21, Maven, Compose и Buildx. Если Docker отсутствует, он также установит Docker из репозитория Debian. Запустите из обычного терминала:

```bash
cd backend
bash scripts/install-debian.sh
```

Скрипт использует `sudo` для установки пакетов и запуска службы Docker. Пароль вводится только в терминале. Права групп и Docker-сокета не меняются. Проверка без установки: `bash scripts/install-debian.sh --check`. Установка выполнена пользователем в обычном терминале; наличие JDK 21, Maven и Compose подтверждено.

```bash
cd backend
cp .env.example .env
docker compose up --build -d
curl http://localhost:8080/api/v1/health
```

API: `http://localhost:8080/api/v1`. Контракт: `http://localhost:8080/openapi.yaml`. Готовность приложения и БД: `/actuator/health`. Данные сохраняются в Docker volume `postgres_data`; обычный `docker compose down` их сохраняет. Порт БД доступен только с localhost. Backend по умолчанию также доступен с localhost; для сетевой демонстрации настройте `BACKEND_BIND` или reverse proxy.

В `.env.example` указаны локальные демонстрационные значения. Compose включает `DEMO_ENABLED=true`: это **вход в заранее подготовленные вымышленные аккаунты без пароля**, включая администратора. Для общего публичного приложения нужна отдельная настоящая авторизация; текущий контракт описывает конкурсный прототип.

## Запуск без контейнера приложения

Нужны JDK 21, Maven 3.6.3+ (рекомендуется 3.9.x) и PostgreSQL 17. Maven должен загружать зависимости из Maven Central.

```bash
cd backend
docker compose up -d db
mvn verify
SPRING_PROFILES_ACTIVE=demo mvn spring-boot:run
```

Параметры: `DB_URL` (по умолчанию `jdbc:postgresql://localhost:5432/sport`), `DB_USER`, `DB_PASSWORD`, `PORT`, `DEMO_ENABLED`, `COOKIE_SECURE`, `CORS_ORIGINS`. Файл `.env` читает Compose; при запуске Java напрямую переменные необходимо передать процессу самостоятельно. Без `demo`-профиля или `DEMO_ENABLED=true` демовход и seed выключены.

Flyway применяет `V1__schema.sql` автоматически. Hibernate работает с `ddl-auto=validate`, не создаёт и не обновляет схему. Seed выполняется один раз в пустой демобазе и не перезаписывает внесённые изменения. Даты будущих событий относительно первого запуска; после их истечения можно создать новые события через API.

## Подключение frontend

[contracts/openapi.yaml](contracts/openapi.yaml) — актуальный контракт, включая регистрацию демопользователя. API использует `joinMode`, `POST .../decision` и `GET /session` согласно этому файлу. Часть ранних примеров в Markdown использует старые имена; объяснение находится в [docs/decisions.md](docs/decisions.md).

```javascript
const response = await fetch('http://localhost:8080/api/v1/demo/session', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ accountId: 'athlete-a' })
});
const session = await response.json();
// На POST/PATCH/DELETE передавайте session.csrfToken в X-CSRF-Token.
// На каждом запросе сохраняйте credentials: 'include'.
```

Cookie `SPORT_SESSION` — HttpOnly; токен CSRF берётся из JSON `/session`. Вход инвалидирует предыдущую сессию и выдаёт новый CSRF. Выход: `DELETE /demo/session` с CSRF. Для смены роли выбирается другой демоаккаунт, а не передаётся `role`/`userId` в произвольном запросе. После входа заново запрашивайте `/session`, чтобы увидеть текущие одобренные организации.

CORS допускает `http://localhost:5173` и `http://localhost:3000`. Другие origin задаются через `CORS_ORIGINS` через запятую. Для HTTPS установите `COOKIE_SECURE=true`; предпочтителен общий origin frontend и API с проксированием `/api`. SameSite=Lax предполагает развёртывание на одном site.

Пагинация: `page=0`, `size=20`, максимум 100. Ответ: `{items,page,size,total,totalPages}`. Ошибка: `{code,message,details,requestId}`; детали — массив полей согласно OpenAPI. `X-Request-Id` помогает сопоставить ответ с серверным журналом. Пользовательский текст возвращается как plain text: frontend должен выводить его текстовыми узлами и не вставлять через `innerHTML`.

## Демонстрационные аккаунты

Полный список демоаккаунтов выдаёт `GET /demo/accounts`, включая пользователей, созданных прежней деморегистрацией. Аккаунты с паролем в него не входят. Скрытого ограничения в 100 аккаунтов нет.

### Регистрация нового пользователя

При `DEMO_ENABLED=true` доступен `POST /api/v1/demo/accounts`. Он создаёт отдельного пользователя в PostgreSQL и сразу выдаёт новую сессию; пароль не требуется. Это демонстрационная авторизация: созданные аккаунты доступны в общем списке для переключения ролей.

```sh
curl -i -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"nickname":"novice-runner","displayName":"Новый участник"}' \
  http://localhost:8080/api/v1/demo/accounts
```

Успех: **201**, `Session` в JSON и HttpOnly-cookie `SPORT_SESSION`. `nickname` — 3–40 символов, `displayName` — 1–100; пробелы по краям обрезаются до проверки длины, nickname уникален без учёта регистра. При ошибке полей/лишних полях — 400, при занятом nickname — 409, при выключенном деморежиме — 404.

Сервер назначает UUID, начальную роль USER, нулевой рейтинг и стабильный `demoAccount`. `POST /demo/accounts` и `POST /demo/session` доступны без CSRF. На последующих POST/PATCH/DELETE нужны cookie и `X-CSRF-Token` из ответа `Session`. Успешная регистрация заменяет только прежнюю сессию этого браузера; неуспешная её сохраняет. Данные существующих демоаккаунтов не изменяются.

Для повторного входа после выхода получите `id` нового аккаунта из `GET /demo/accounts` и передайте его как `accountId` в `POST /demo/session`. Этот `id` не равен UUID профиля и остаётся прежним после изменения nickname. Пользователь и профиль сохраняются при перезапуске; сессии по-прежнему хранятся в памяти приложения.

Frontend после 201 очищает приватный кэш, сохраняет `Session` и новый `csrfToken` так же, как при переключении аккаунта. UI регистрации, публичный профиль (`GET /users/{id}`) и `requirements` подключены в ветке `frontend`; [критерии и статус задач](../frontend/docs/TZ_GAPS_FRONTEND.md).

| accountId | Назначение |
|---|---|
| `athlete-a`, `athlete-b`, `athlete-c` | Пользователи и участники |
| `coach` | Автор демособытий, тренер и спортивный организатор |
| `referee` | Судья, отдельно назначенный на демосоревнования |
| `org-approved` | Представитель одобренного клуба «Темп» |
| `org-pending` | Представитель организации «Новый старт», ожидающей решения |
| `org-rejected` | Представитель отклонённой организации «Вектор» |
| `admin` | Административная модерация |

У `athlete-b` в seed 20 баллов за два проверенных соревнования; третье завершённое соревнование позволяет показать +10 и переход в `ACTIVE`. Остальные начальные рейтинги равны нулю. Есть личный диалог A↔B, групповой чат клуба, заполненное событие с очередью, черновик и снятое событие. UUID детерминированы; для работы frontend следует получать их из API.

Полный API-прогон обязательных сценариев: [scripts/smoke.py](scripts/smoke.py). Пошаговая демонстрация: [docs/demo.md](docs/demo.md).

```bash
python3 scripts/smoke.py --base http://localhost:8080/api/v1
```

Скрипт создаёт собственные вымышленные события и организации через HTTP, проверяет результат под разными ролями, обе ветви решений и запреты. Не очищает общую базу.

## Проверки

```bash
# Из папки backend/
mvn verify                     # JUnit, MockMvc, H2 PostgreSQL mode; Docker не нужен
mvn -Ppostgres-it verify       # также S1–S6, расширения и конкурентные запросы в PostgreSQL/Testcontainers
```

Второй вариант требует доступного Docker daemon. PostgreSQL-тесты не помечены как пропущенные при отсутствии Docker: команда должна завершиться ошибкой, если выполнить их нельзя. Отдельный автоматический workflow `../.github/workflows/backend.yml` подготовлен для GitHub Actions; в GitVerse команды нужно включить в его CI.

Для статической сверки API нужен Python 3 и PyYAML:

```bash
python3 -m pip install pyyaml
python3 scripts/check_contract.py
```

**Проверки исходной ветки backend до переноса:** полный `mvn verify` завершился **BUILD SUCCESS**, все **23 теста** прошли, включая пять конкурентных сценариев на H2. Исполняемый JAR собран. Логи пользовательского запуска подтверждают работу PostgreSQL и backend в Docker, успешный HTTP smoke S1–S6, очереди и чатов. Полный профиль PostgreSQL/Testcontainers ещё не запускался: Docker daemon недоступен из изолированной сессии агента. Точные результаты: [docs/verification.md](docs/verification.md).

## Правила и ограничения

- Системные права, владение, допуск организации, лимиты и автор сообщения определяет сервер. Спортивная роль в профиле не даёт прав администратора или судьи на чужих соревнованиях.
- `OPEN` сразу создаёт `CONFIRMED`; `APPROVAL` создаёт `PENDING`, решение принимает только организатор. Дубликаты запрещены; отменённую регистрацию можно подать повторно. Отклонённую заявку повторно подать нельзя.
- Места занимают только `CONFIRMED`. Все изменения блокируют строку события в транзакции. Очередь только для заполненного `OPEN`; отмена участника автоматически подтверждает запись первого ожидающего. Изменение лимита при существующей очереди запрещено.
- Снятие с публикации сохраняет регистрации и причину. Карточка видна владельцу, администратору и ранее зарегистрированным; новые записи запрещены. Восстановление модератором не предусмотрено контрактом; `/publish` предназначен для черновиков.
- Рейтинг: +10 за верифицированное участие в завершённом `COMPETITION` с `endsAt`; `ROOKIE` 0–29, `ACTIVE` 30–79, `EXPERIENCED` 80–159, `ELITE` 160+. Проверяет организатор или назначенный на конкретное событие судья; проверять собственное участие нельзя. Повтор возвращает ту же проводку. Проводки и факт верификации записываются атомарно. Это внутренний показатель активности; внешней проверки посещения нет.
- Снятие уже проверенного соревнования **сохраняет ранее начисленные баллы**, новые начисления запрещены. Автоматического отзыва и API корректировок контракт не содержит.
- Рекомендации: +50 за любимый спорт, +20 за уровень, +20 за предпочитаемое время, +10 за места. Время сравнивается в UTC, поскольку в контракте нет часового пояса профиля; используемые интервалы указаны в ADR. Текущая реализация сортирует кандидатов в памяти, подходит для прототипа.
- Direct доступен только двум участникам, включая запрет для постороннего администратора. Community доступен активным членам одобренной организации; после выхода закрыта вся история, после повторного свободного вступления доступ восстанавливается. Исключение другого участника, жалобы и модерация приватных сообщений требуют дополнительных API.
- Переписка работает через HTTP и пагинацию; frontend может использовать polling. WebSocket, загрузка файлов, парольная авторизация и восстановление пароля не входят в текущий API. Новые демопользователи создаются через `POST /demo/accounts`.
- Встроенного rate limiting, внешних уведомлений и загрузки файлов нет. При внешнем размещении ограничения запросов можно настроить в reverse proxy.
- Аватары — внешние HTTP(S) URL, сервер их не загружает; frontend должен показывать fallback при ошибке загрузки.
- Сессии хранятся в памяти одного экземпляра сервиса и теряются при перезапуске. Бизнес-данные хранятся в PostgreSQL. Для нескольких экземпляров потребуется общее хранилище сессий.

## Карты и геокодинг

Новые публичные GET: `/api/v1/geo/suggest?q=...&city=...&limit=5`, `/geo/reverse?latitude=...&longitude=...`, `/map/events?bbox=...`, `/map/venues?bbox=...`. Полный контракт и типы — `contracts/openapi.yaml`. `bbox` всегда **west,south,east,north**, охват до 10° на ось. `limit` 1–500 (по умолчанию 300), `sportId` — необязательный UUID. События дополнительно принимают `from/to` с timezone; возвращаются только будущие PUBLISHED с обеими координатами, по startsAt/id. `truncated=true` требует приблизить карту.

Миграция `V2__sports_map.sql` добавляет площадки, историю оценок и индексы; V1 и пользовательские события не изменяются. POST `/map/venues` и `/map/venues/{venueId}/reports` требуют прежние cookie-сессию и CSRF. Автор берётся из сессии и не публикуется в ответах. Ограничения: 3 новые площадки/час/аккаунт; совпадающее имя ближе 30 м — 409; оценка конкретной площадки одним пользователем раз в 10 минут — 429 с Retry-After. Повторные отчёты сериализованы блокировкой площадки. Защита от дублей — предварительная проверка, не строгая пространственная уникальность при создании разными пользователями одновременно.

LOW/MEDIUM/HIGH — субъективные оценки очевидцев; peopleCount (0–1000) не определяет уровень. Свежими считаются последние оценки каждого пользователя за 90 минут (граница исключена); итог — верхняя медиана. UNKNOWN означает отсутствие свежих данных. История сохраняется; lastReportedAt может быть устаревшим, reportsCount учитывает уникальных свежих авторов. validUntil — ближайшее истечение оценки в агрегате, после которого результат надо перечитать. Время задаётся серверным Clock. Площадки и отчёты для окна загружаются пакетно. Проекция мероприятий переиспользует существующий Views.card() и наследует его дополнительные запросы.

Для настоящих адресов задайте `GEOAPIFY_API_KEY` в `backend/.env` (Compose передаёт его приложению), затем пересоздайте backend. Без ключа приложение стартует, только геомаршруты возвращают структурированную 503. Карта и ручное создание событий остаются доступны. Геоадаптер использует [Geoapify autocomplete](https://apidocs.geoapify.com/docs/geocoding/address-autocomplete/) и [reverse](https://apidocs.geoapify.com/docs/geocoding/reverse-geocoding/), русский язык, URL encoding, connect timeout 3 с / request timeout 4 с, cache 5 минут / до 512 записей, общий бюджет 120 поисковых операций/минуту на экземпляр. Ошибки поставщика, включая 429, нормализуются в 503. Ключ не передаётся frontend и не включается в сообщения ошибок. Публичный Nominatim не используется. При больших нагрузках нужны распределённые лимиты/кеш и ограничения по клиентам на reverse proxy.

Демо-площадки явно отмечены как условные объекты возле площади Куйбышева; исходная опорная координата сверена с [Wikidata](https://www.wikidata.org/wiki/Q4365616). Они не обозначают реальные спортивные сооружения. Seed идемпотентен, запускается только с DEMO_ENABLED=true, добавляет недостающие объекты без перезаписи существующих; свежие оценки не «оживляются» на каждом старте.

Примеры после запуска (получение сессии и csrf — как в разделе демовхода):

```sh
curl 'http://localhost:8080/api/v1/map/venues?bbox=49.8,53.0,50.4,53.5&limit=300'
curl 'http://localhost:8080/api/v1/map/events?bbox=49.8,53.0,50.4,53.5'
curl -G 'http://localhost:8080/api/v1/geo/suggest' --data-urlencode 'q=площадь Куйбышева' --data-urlencode 'city=Самара'
curl 'http://localhost:8080/api/v1/geo/reverse?latitude=53.195561&longitude=50.101022'
curl -b cookies.txt -H "X-CSRF-Token: $csrf" -H 'Content-Type: application/json' \
  -d '{"name":"Площадка для игры","location":{"city":"Самара","address":"площадь Куйбышева","latitude":53.195561,"longitude":50.101022}}' \
  'http://localhost:8080/api/v1/map/venues'
curl -b cookies.txt -H "X-CSRF-Token: $csrf" -H 'Content-Type: application/json' \
  -d '{"level":"LOW","peopleCount":5}' \
  "http://localhost:8080/api/v1/map/venues/$venueId/reports"
```

### Подключение API-ключа

Если Geoapify Autocomplete не находит адрес (в частности, часть улиц Самары), адаптер делает дополнительный запрос полного геокодирования `/geocode/search`. Результат кешируется как обычная подсказка. Лимит 120 поисковых операций/минуту на экземпляр в этом случае допускает до 240 HTTP-запросов поставщику; reverse использует один запрос.

1. В [Geoapify MyProjects](https://myprojects.geoapify.com/) создайте проект, откройте **API Keys** и скопируйте ключ. Он используется для Address Autocomplete и Reverse Geocoding.
2. В `backend/.env` задайте `GEOAPIFY_API_KEY=ваш_ключ` без кавычек и пробелов. Если файла ещё нет, скопируйте `.env.example`; существующий `.env` сохраняйте. Ключ остаётся на сервере, не добавляйте его в Git или переменные `VITE_*`.
3. Для Docker из `backend/` выполните `docker compose up -d --force-recreate backend`. Если запускали через `scripts/start-local.sh`, используйте `bash scripts/start-local.sh --skip-build`. Перезапуск процесса сам по себе не обновляет окружение существующего контейнера.
4. При запуске Java через Maven Compose не передаёт `.env` приложению. В терминале из `backend/` выполните:

   ```bash
   read -r -s -p 'Geoapify API key: ' GEOAPIFY_API_KEY
   printf '\n'
   export GEOAPIFY_API_KEY
   mvn spring-boot:run
   ```

5. Проверьте два запроса из примеров выше: `/geo/suggest` должен вернуть 200 и `items`, `/geo/reverse` — 200 и `location`. В интерфейсе введите город и от трёх символов адреса, выберите подсказку или нажмите на карту: адрес и метка заполнятся вместе. Если ключ ограничен у поставщика, разрешите исходящий IP сервера; запросы отправляет backend.

Без ключа доступны выбор точки и создание площадки с ручным адресом. Клик по карте сохраняет введённый текст, пока определяется адрес; при ошибке геокодера его можно исправить и подтвердить кнопкой «Подтвердить адрес точки». Успешный ответ геокодера заменяет текст найденным адресом, сохраняя точные координаты клика.

Подложка MapLibre/OpenFreeMap работает без API-ключа и настраивается через `VITE_MAP_STYLE_URL`. Подробнее: [frontend/docs/MAPS.md](../frontend/docs/MAPS.md).

Перед POST-примерами получите cookie и csrfToken: `curl -c cookies.txt -H 'Content-Type: application/json' -d '{"accountId":"athlete-a"}' http://localhost:8080/api/v1/demo/session`. В переменную `csrf` запишите возвращённый csrfToken, в `venueId` — UUID созданной площадки. Для браузерных тестов `cd frontend && npm run test:e2e:api` добавьте `http://127.0.0.1:5174` в CORS_ORIGINS и оставьте GEOAPIFY_API_KEY пустым: сценарии карт проверяют ручной fallback на настоящем Java API.
