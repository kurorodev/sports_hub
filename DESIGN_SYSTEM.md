# DESIGN_SYSTEM.md — Визуальная система «Sports Hub» v0.1

> Статус: **предлагаемое направление, подлежит утверждению фронтенд-командой**. Не является официальным брендбуком Столото. Система намеренно построена через токены, чтобы позже менять визуальную тему без переписывания бизнес-компонентов.
>
> Концепция: **Stoloto-inspired, sport-first**. Чувство принадлежности к продуктовой экосистеме Столото достигается контрастом, энергичным жёлтым акцентом, ясной типографикой и крупными интерактивными элементами. Но продукт про **людей, спорт и встречи**, не про лотерею. Избегать буквального копирования сайта, логотипа и коммерческой айдентики.

## 1. Образ продукта и визуальные принципы

- Характер: энергичный, дружелюбный, современный, уверенный, понятный новичку и взрослому.
- Функция важнее декора: за несколько секунд ясно, **какой спорт, когда, где, с кем и как записаться**.
- Светлый интерфейс по умолчанию; тёмные выразительные hero/навигационные поверхности — контрастный акцент.
- Жёлтый — цвет **основного действия, активного состояния и точечного внимания**, а не заливка всего экрана.
- Спортивная фотография: люди и реальные активности, разнообразие дисциплин (включая шахматы), а не только фитнес/экстрим. Не выдавать стоковый снимок за фото реального мероприятия.
- Ни один экран не должен ощущаться как промо-лендинг вместо продукта: в первом viewport должна быть возможность найти событие или создать его.

## 2. Цветовые токены (начальный вариант, не брендбук)

| Token | Hex | Назначение |
|---|---|---|
| `--color-brand` | `#FFCC16` | primary CTA, активная вкладка, ключевой action |
| `--color-brand-hover` | `#F4BD00` | hover primary |
| `--color-ink` | `#151419` | главный текст, тёмная навигация |
| `--color-ink-muted` | `#65656D` | вторичный текст |
| `--color-canvas` | `#F5F5F3` | фон приложения |
| `--color-surface` | `#FFFFFF` | карточки/формы |
| `--color-surface-alt` | `#EFEFED` | спокойные зоны/фильтры |
| `--color-outline` | `#DEDEDC` | границы и разделители |
| `--color-focus` | `#245FE5` | высококонтрастное кольцо фокуса |
| `--color-success` | `#16734A` | подтверждено |
| `--color-warning` | `#9C5C00` | ожидание/предупреждение |
| `--color-danger` | `#B72C3A` | отклонение/ошибка/опасное действие |
| `--color-info` | `#245FE5` | справка/информация |

CSS tokens — единственный источник цветов; цвет статуса всегда сопровождается текстом и/или иконкой. Проверять контраст WCAG AA для текста (4.5:1 обычный текст, 3:1 крупный) и интерфейсных границ (3:1 там, где применимо). Жёлтый фон + чёрный текст; не использовать белый текст на жёлтом. Для status chips разрешены спокойные tinted-фоны с тёмным текстом.

Предложение для реализации:

```css
:root {
  --color-brand: #ffcc16;
  --color-brand-hover: #f4bd00;
  --color-ink: #151419;
  --color-ink-muted: #65656d;
  --color-canvas: #f5f5f3;
  --color-surface: #ffffff;
  --color-surface-alt: #efefed;
  --color-outline: #dededc;
  --color-focus: #245fe5;
  --color-success: #16734a;
  --color-warning: #9c5c00;
  --color-danger: #b72c3a;
  --color-info: #245fe5;
}
```

**Не привязывать цвета бизнес-статусов напрямую к API enum в JSX:** central map `status → {label, semanticTone, icon}`. Тема допускает будущую замену палитры.

## 3. Типографика

- Предпочтение: `Manrope` или `Onest` с локальной/разрешённой поставкой webfont; fallback `Inter`, `Arial`, sans-serif. Выбрать и зафиксировать **один** семейственный набор в проекте; не блокировать приложение при недоступности шрифта.
- Hero/display: `clamp(2.25rem, 5vw, 4.5rem)`, weight 750–800, line-height 1.02–1.12; использовать только там, где уместно.
- H1 страницы: `clamp(1.75rem, 3vw, 2.5rem)`, 700–800.
- H2: `clamp(1.375rem, 2vw, 1.875rem)`, 700.
- H3: `1.125–1.375rem`, 650–700.
- Основной текст: `1rem / 1.5–1.6`; вторичный `0.875rem / 1.4–1.5`.
- Подписи `0.75–0.8125rem` только для вспомогательного контента, не скрывать важные условия мелким кеглем.
- Не делать всю страницу жирным uppercase, даже если на промоматериалах Столото встречается такой стиль. Верхний регистр допустим для коротких категорий/лейблов.

## 4. Пространство, радиусы и поверхности

Использовать 4/8-пиксельную систему: `4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80` px. Рекомендуемые токены: `--space-1: 4px` ... .

- Контейнер desktop: max-width `1280–1360px`, горизонтальные отступы `24–40px`.
- Tablet: боковые отступы `24px`; mobile: `16px` (при 320px допускается `12px`).
- Card radius `20–24px`, button/input `12–16px`, панель/модальный блок `24–28px`, pill `999px`. Не назначать индивидуальный radius каждому экрану.
- Карточки на белом фоне, умеренные тонкие outline, очень мягкая тень только при необходимости для отделения плавающего элемента. Избегать жирных теней и «нейросеточного glass».
- Touch targets — не меньше ~44×44 CSS px; расстояния между целями достаточные для пальца.

## 5. Layout и breakpoints

| Ширина | Стратегия |
|---|---|
| 320–374px | сжатая мобильная версия, 1 колонка, полные CTA |
| 375–767px | mobile, 1 колонка событий, компактная навигация |
| 768–1023px | tablet, 2 колонки каталога при достаточном месте |
| 1024–1439px | desktop, фильтры сбоку, 2–3 колонки |
| 1440px+ | широкая версия с ограниченным max-width, 3–4 колонки при возможности |

Это **контрольные диапазоны, не требования заказчика**. Не навязывать искусственные breakpoint, если контенту тесно: предпочтительны CSS Grid `minmax`, `auto-fit` и container queries, где оправдано. Проверять: 320, 375, 768, 1024, 1440 px. Не допускать глобальный horizontal overflow.

**Навигация:** desktop — видимая шапка (бренд, «Активности», «Создать», «Организации», «Сообщения» по доступности и стадии, профиль); mobile — компактная шапка + доступная нижняя панель только для **реально работающих** ключевых разделов. Можно вдохновиться округлой тёмной панелью Столото, но использовать собственные пропорции и группировку. Избегать перекрытия контента: учитывать safe-area и нижний padding.

**Админка:** desktop — фильтры + таблица/список; mobile — стопка содержательных карточек со статусом и явными действиями. **Организация:** dashboard с заявкой и состоянием; заблокированная публикация до допуска, причина отказа видна.

## 6. Библиотека компонентов (собственные UI primitives)

Строить компоненты только по реальному использованию; все доступны клавиатурой и с видимым focus-visible.

| Компонент | Варианты / правила |
|---|---|
| `Button` | `primary` жёлтый / `secondary` контур / `tertiary` текст / `danger` с подтверждением; loading/disabled |
| `TextField`, `Textarea`, `Select`, `Combobox` | visible label, hint, error, required, clear; sport combobox поддерживает «Свой вид спорта» |
| `Card`, `EventCard` | спорт, название, дата, место, уровень, организатор, режим, состояние и ясный CTA; не перегружать |
| `StatusBadge` | `PENDING`, `CONFIRMED`, `REJECTED`, `APPROVED`, `UNPUBLISHED`, `WAITLISTED` и др. только из OpenAPI |
| `Tabs`, `Chip`, `FilterBar` | выбранность очевидна без одного цвета, URL search params где целесообразно |
| `Dialog`, `Drawer` | focus trap, ESC, возврат фокуса, подтверждение destructive, mobile bottom sheet там, где уместно |
| `EmptyState`, `ErrorState`, `Skeleton`, `Toast` | каждое состояние полезно и даёт следующий шаг |
| `Pagination`, `Avatar`, `OrganizerLink`, `UserLink` | переиспользуемость без доменной путаницы |
| `JoinAction` | один компонент, все серверные `joinMode`/viewer statuses; повторная запись недоступна |

Анимации: 120–220ms для микроинтеракций, 220–320ms для панелей; transform/opacity; учитывать `prefers-reduced-motion`; не делать задержку обязательного действия ради эффектов.

## 7. Экраны и визуальная иерархия

### Публичные / пользователь

1. **Главная/каталог** — ключевое предложение «Найди свою компанию для спорта», поиск/фильтры, ближайшие события; популярные дисциплины по данным, а не псевдостатистика. Hero небольшой, без необходимости длинной прокрутки до событий.
2. **Каталог** — понятные фильтры (спорт/место/дата/уровень/режим/наличие мест), адаптивная сетка, сортировка/пагинация, отсутствие результатов → «Создать мероприятие».
3. **Карточка мероприятия** — заголовок, фото только при наличии допустимых ресурсов, дата/время/место/уровень, организатор, доступные места, условия, участники, отдельный блок обсуждения; основной CTA заметен в mobile viewport.
4. **Создание** — последовательная форма по смысловым блокам: что/где-когда/кому-подходит/как присоединиться/публикация; выбор вида спорта + свой; серверная ошибка у соответствующего поля.
5. **Мои события/мои участия** — разные вкладки; события автора, ожидающие заявки, подтвержденные участия и отклонения.
6. **Профиль пользователя** — публичная и собственная версии; P1 редактирование, P2 история ранга; спортивная роль **не** равна правам сайта.
7. **Сообщения** (P2) — 2-панельный desktop / список и отдельный чат mobile, private vs community distinction, запрещённый доступ → корректное состояние.

### Организация

8. Заявка организации / ожидание / отказ с причиной / одобрение, публичная страница с событиями, управление заявками и обсуждениями.

### Админ

9. Поиск и модерация заявок организаций с двумя исходами и причиной; события со статусами, организатором и переходом в обсуждение; модерация **отдельного** сообщения; причины снятия события.

## 8. Понятные состояния как часть дизайна

- `OPEN` без участия: «Присоединиться»; после успешного ответа сервера — «Вы участвуете».
- `APPROVAL` без заявки: «Подать заявку»; `PENDING`: «Ожидает решения»; `CONFIRMED`: «Вы участвуете»; `REJECTED`: «Заявка отклонена» (причина — если доступна).
- `PUBLISHED`: доступно для записи с учётом мест и прав; `UNPUBLISHED`: «Снято с публикации», причина и блокировка действия.
- `ORGANIZATION PENDING`: «Заявка на рассмотрении»; `APPROVED`: «Организация подтверждена»; `REJECTED`: «Заявка отклонена» + reason.
- `404` для отсутствующей собственной записи (`/my-registration`) — нейтральное состояние «Вы ещё не записаны», а не «Сбой сервера».
- Ошибка сети — короткое объяснение и «Повторить», без stack trace; empty search — предложение скорректировать фильтры/создать свою встречу.
- Асинхронные запросы: skeleton либо прогресс, блокировать повторные мутации до ответа; `success` только после фактического ответа API.

## 9. Изображения, иконки и бренд

- Промофотографии спорта — только с правом использования; внутренние карточки не должны требовать внешнего CDN для корректности демо. Сохранять alt text, фиксированное aspect-ratio, `object-fit: cover`, lazy loading.
- Не создавать «лотерейные карточки» и фальшивые цены/призы. Кейс — спорт и встречи, не продажа билетов.
- Не встраивать логотип Столото, не заявлять «официальный дочерний продукт», пока команда не получила разрешения/подтверждения. Допустимо нейтральное упоминание «Конкурсный проект по кейсу Столото» в презентации/описании.
- Название и знак проекта оформлять как заменяемые `BrandLogo/BrandName`, чтобы смена «Sports Hub» не требовала массового редактирования файлов.

## 10. Внедрение: от каркаса к polished UI

- **Design baseline сейчас:** палитра, шрифт, радиусы, сетка, кнопки/поля, адаптивная навигация, event-card. Зафиксировать в tokens/CSS/компонентах.
- **Функциональный UI:** в приоритете S1–S6, состояния, все моки соответствуют API; на каждом модуле проверить desktop+mobile.
- **Интеграция:** замена mock-транспорта реальным Java API; UI не должен меняться только из-за нового URL.
- **Полировка:** фотография, микровзаимодействия, точность отступов, композиция, визуальная уникальность, аудит контраста; возможный ребрендинг через токены и Brand-component, но без нарушения доступности/сценариев.
- **Приёмка дизайна:** единообразие карточек/форм/статусов в трёх ролях; человек понимает действие и результат; mobile проверен; отсутствуют клишированные AI-элементы; на скринкасте ключевой путь читается и без комментариев разработчика.

## 11. Правила для Codex при разработке интерфейса

1. Перед задачей уточни экран, пользовательскую задачу, состояния и связанные API. Переиспользуй токены и primitives.
2. Не подменяй дизайн-систему готовым шаблоном и не копируй чужие сайты 1:1. Если есть утверждённый макет или референс — максимально сохраняй **согласованные** решения композиции/типографики, а не придумывай свои.
3. Не используй временный inline-style/случайный цвет/отступ там, где есть токен. `className` отвечает за расположение; доменные статусы должны проходить через централизованную семантическую карту.
4. Каждый изменённый экран проверить mobile+desktop, keyboard focus, long text, пустые данные, ошибки, 320px overflow. Не убирать обязательную функцию на мобильном.
5. При запросе «сделай красивее» менять **только визуальный слой**, не переписывая API, маршруты, бизнес-логику и тесты без явной причины.

**Критерий качества:** приложение ощущается самостоятельным спортивным продуктом из визуальной семьи Столото, но пользователь сразу понимает, куда нажать, чтобы найти компанию, создать встречу и записаться.
