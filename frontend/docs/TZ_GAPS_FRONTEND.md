# Задачи frontend по результатам проверки исходного ТЗ

Дата: 19.10.2026. Базовый аудит: `641a763`. **Все три задачи ниже реализованы в ветке `frontend`**: профиль из `0ae2ef2` дополнен ссылками в каталоге/админке, backend регистрации объединён, экран `/register` подключён, условия участия вводятся и отображаются. Результаты проверок — в [QA.md](QA.md). Ниже сохранены исходные требования и критерии приёмки; формулировки проблем относятся к версии аудита.

Основание: [аудит ТЗ](../../backend/docs/tz-audit-2026-10-19.md), [исходное задание](../../backend/docs/source/case-brief.pdf). Номера страниц PDF ниже включают титульную страницу.

Цель — закрыть три найденных пробела: переход к организатору-пользователю, отображение условий участия и экран регистрации. Карта и другие дополнительные возможности в эту задачу не входят.

## Готовность backend и зависимости

| Функция | Что уже есть | Зависимость frontend |
|---|---|---|
| Публичный профиль организатора | `GET /api/v1/users/{userId}`, DTO `UserProfile`; доступен гостю | Можно делать сейчас, API менять не требуется |
| Условия участия | `requirements` в `Event`, `EventCreate`, `EventPatch`; сохранение и возврат из БД | Ввод и отображение подключены |
| Вход | `GET /api/v1/demo/accounts`, `POST /api/v1/demo/session`, `GET /api/v1/session` | Работает для существующих демоаккаунтов |
| Создание нового демоаккаунта | `POST /api/v1/demo/accounts` → 201/Session и HttpOnly-cookie | `/register` подключён к обновлённому OpenAPI |

ТЗ разрешает имитацию регистрации и входа: production-auth, пароль и подтверждение почты не обязательны. В этой ветке backend уже создаёт отдельного демопользователя; это выбранный способ реализации, а не отдельное требование исходного задания. Если команда выбирает только демонстрационный экран без создания аккаунта, это нужно явно обозначить в UI и документации; нельзя показывать сообщение «новый аккаунт создан» после входа в существующий или изменения чужого демопрофиля.

Реализованный backend и результаты проверки: [tz-gaps-backend.md](../../backend/docs/tz-gaps-backend.md). `POST /api/v1/demo/accounts` добавлен в OpenAPI, runtime-схемы и generated-типы. Для frontend доступны все три серверные зависимости. При переносе задачи заберите актуальную ветку backend целиком, включая контракт.

## 1. Профиль организатора-пользователя

### Требование и текущая проблема

ТЗ, страницы 3 и 6: карточка мероприятия содержит организатора и переход к его профилю/странице; организатор доступен из административного просмотра.

Ссылки на организации уже работают. В случае `organizer.type === "USER"` сейчас выводится только имя, а пользовательского маршрута нет.

### Реализация

1. Добавить маршрут `/users/:userId` и страницу публичного профиля.
2. Читать профиль через существующий `GET /api/v1/users/{userId}`. Использовать generated `components["schemas"]["UserProfile"]`; при необходимости добавить его экспорт в `shared/api/types.ts`. Не создавать собственный несовместимый DTO.
3. Для базовой страницы показать `displayName`, `nickname`, доступные `bio`, `city`, фото с fallback. Не выводить пустые необязательные поля. Данные брать из API, не из списка демоаккаунтов.
4. Показать загрузку, 404, ошибку сети с повтором; корректно отменять устаревший запрос при смене пользователя. Чтение гостем должно работать.
5. Заменить имя USER на ссылку `/users/{organizer.id}` в:
   - `src/pages/event/ui/EventPage.tsx`;
   - `src/entities/event/ui/EventCard.tsx`;
   - `src/features/moderate-content/ui/ModerationEventCard.tsx`.
6. Сохранить существующие переходы ORGANIZATION → `/organizations/{id}`.
7. Соблюсти текущие FSD-границы: сборка страницы в `pages`, пользовательские данные/API в соответствующем модуле `entities`, транспорт в `shared/api`.

Редактирование профиля, история рейтинга, личные сообщения и список всех событий автора для закрытия этого пункта не требуются.

### Приёмка

- Гость открывает личное событие → нажимает имя организатора → видит профиль этого пользователя.
- Администратор переходит к тому же профилю из административной карточки события.
- Прямая ссылка и reload работают; неизвестный UUID показывает 404-состояние.
- Переход к организации продолжает работать.

## 2. Условия участия (`requirements`)

### Требование и текущая проблема

ТЗ, страницы 3–4: пользователь должен понимать условия участия, включая подготовку и инвентарь, если они есть.

Проверенный пример: у события «Футбол во дворе» API возвращает `requirements: "Удобная одежда и вода"`, но страница этот текст не показывает.

### Реализация

1. В `EventPage.tsx` добавить блок «Условия участия» для непустого `event.requirements`.
2. Выводить пользовательский текст обычными React-узлами, сохраняя переносы строк; не использовать `innerHTML`.
3. При `null` или пустом тексте не показывать пустой блок. Уровень подготовки и OPEN/APPROVAL продолжать выводить отдельно.
4. Для единообразного ввода добавить в форму создания необязательное поле «Условия участия / что взять с собой», максимум **2000** символов по текущему контракту. Это выбранное улучшение формы: само ТЗ не требует отдельного поля и допускает условия в общем описании.
5. Передавать значение в существующий `EventCreate.requirements`; пустое поле нормализовать в `null` либо не отправлять. Согласованно обновить:
   - `shared/api/event-schema.ts` — сейчас strict-схема не описывает `requirements`;
   - `features/create-event/ui/create-event-form.ts` — значения формы, преобразование и отображение серверных ошибок;
   - `features/create-event/ui/CreateEventForm.tsx`;
   - MSW/фикстуры, если их текущие преобразования теряют это поле.
6. Использовать уже существующий контракт и лимит. Backend или миграции для этого не нужны.

### Приёмка

- У существующего события виден сохранённый `requirements`, даже если его нет в `description`.
- Создание события с условиями → reload → другой пользователь видит тот же текст.
- При пустых условиях форма и карточка работают.
- Граница 2000 символов, превышение лимита, переносы и текст с HTML-символами обрабатываются корректно.
- После серверной ошибки значения формы сохраняются; существующие организация, спорт и координаты не теряются.

## 3. Экран демонстрационной регистрации

### Требование и граница работы

ТЗ, страница 5: нужны экраны регистрации и входа, при этом авторизацию можно имитировать. Существующие `/demo/session` и `/me/profile` не создают пользователя.

В действующем потоке новый пользователь сохраняется backend в демонстрационной БД. Форма не должна менять `athlete-a`, `coach` или другой уже существующий демоаккаунт под видом регистрации.

### Подключение действующего backend-контракта

1. Добавить маршрут `/register`, переход «Создать аккаунт» со страницы входа и обратный переход к входу.
2. Отметить режим: «Демонстрационная регистрация, без пароля». Не обещать подтверждение почты или защищённый парольный вход.
3. Поля `DemoRegistrationRequest`: `nickname` (3–40), `displayName` (1–100). Пробельные значения не считать заполненными. Ограничения брать из актуального OpenAPI.
4. Отправлять `POST /api/v1/demo/accounts` с `{nickname, displayName}`. Не добавлять скрытый fallback на моки при ошибке реального API. Ошибки: 400 — валидация, 409 — занятый nickname, 404 — деморежим выключен.
5. Успехом считать только успешный ответ сервера. Backend возвращает `201` с существующим DTO `Session` и HttpOnly-cookie `SPORT_SESSION`.
6. После успеха использовать существующую логику смены аккаунта: отменить старые запросы, очистить приватный query cache, сохранить `csrfToken` в транспорт и `Session` в session query. Cookie из JavaScript не читать.
7. Сохранять разрешённый контекст перехода, как при входе: создание встречи, запись, обсуждение, карта и кабинет организации. Проверять внутренний адрес возврата существующими helpers.
8. Показывать ошибки полей и занятый nickname; сохранять форму, блокировать повторную отправку на время запроса. Не обещать идемпотентность повторной регистрации после сетевого обрыва, если она не появится в контракте.
9. Синхронизировать MSW с новым утверждённым DTO. В mock-режиме моделировать отдельного пользователя; в real-режиме сессия и бизнес-данные берутся только с backend.

### Приёмка полного потока

- Гость открывает регистрацию, заполняет поля и получает нового пользователя и рабочую сессию.
- После reload остаётся в своём аккаунте; может создать встречу, видимую другому пользователю.
- Новый пользователь не получает ADMIN или права одобренной организации.
- Занятый nickname возвращает понятную ошибку, а не вход в одноимённый аккаунт.
- После выхода доступен повторный демонстрационный вход в созданный аккаунт по согласованному механизму backend.
- Фиксированные демоаккаунты и их данные после регистрации не изменились.
