# Проверка frontend

## Ограничения календарей

В создании встречи календарь начинается с сегодняшнего дня в выбранном часовом поясе места встречи. Ручной ввод прошедшей даты или времени блокирует публикацию с ошибкой у поля. В каталоге и на карте обе границы начинаются с сегодняшнего дня UTC; дата окончания не может предшествовать началу. Недопустимый ручной ввод не меняет активный фильтр и URL. Очистка границ разрешена. Лимиты обновляются при возвращении на вкладку и раз в минуту.

Регрессия: `npm test -- src/tests/date-range.test.tsx src/tests/create-event.test.tsx` и `npm run test:e2e -- e2e/date-filters.spec.ts e2e/create-event.spec.ts e2e/map-navigation.spec.ts --workers=2`. Браузерные сценарии дат работают на сетевых моках; изменение API не требуется.

## Ручной путь на Java

1. Поднять Docker/OrbStack, Java и PostgreSQL; запустить `npm run dev`, открыть `http://localhost:5173`. Убедиться, что нет отметки о локальных моках.
2. На `/login` выбрать Алексея (`athlete-a`). Создать встречу, указать свой спорт, будущую дату, время с поясом, свободную запись и 2 места. Дождаться подтверждения публикации. Перезагрузить — запись сохранена.
3. Войти Марией (`athlete-b`), найти встречу по названию либо новому спорту. Открыть и нажать «Присоединиться». Должны появиться «Вы участвуете», 1 из 2 и Мария в «Кто идёт». Перезагрузить и проверить статус в каталоге.
4. Переключиться на Алексея: он видит Марию, актуальное число участников и свою отметку организатора. Кнопка записи ему не предлагается.
5. Войти Ириной (`athlete-c`) и занять второе место. Представитель клуба (`org-approved`) увидит заполненную встречу. Повторная запись не создаёт дубликат.
6. Под администратором (`admin`) открыть `/admin`, затем под обычным пользователем проверить запрет. Кабинет рассматривает заявки организаций; модерация мероприятий/комментариев доступна в отдельных разделах.
7. Проверить поиск, спорт, уровень, даты (UTC), пустую выдачу и сброс. Открыть `/events/not-a-uuid` для not-found. Проверить клавиатуру, видимый фокус, 375/768/1440 px и отсутствие общего горизонтального скролла.

На Java время из введённого offset возвращается в UTC: например, 18:30 UTC+07 — это 11:30 UTC. Пояс подписан возле времени; момент события сохраняется.

## Что доказал реальный браузерный прогон

S1/S3 на 375/768/1440: вход через UI → HttpOnly SPORT_SESSION → личное создание с произвольным новым спортом → 201 и правильный момент времени → reload → другой аккаунт находит событие → 404 собственной записи является нормальным отсутствием → POST без CSRF отклонён → UI с правильным CSRF получает 201/CONFIRMED → статус/численность/PublicUser обновлены → reload сохраняет участие → повторный POST возвращает 409 → организатор видит участника → другой пользователь заполняет второе место → следующий аккаунт видит отсутствие мест. Также проверены доступ ADMIN и очистка прав при переключении на USER.

Service workers в этом прогоне заблокированы, ответы создания и записи проверяются как полученные без service worker. Это запросы к Java, а не к MSW. Данные хранятся в PostgreSQL Docker volume. Подключение использует Vite proxy, поэтому независимое production-развёртывание этим не подтверждено. Реальные desktop/mobile скриншоты просмотрены визуально.

## S4: ручной путь на Java

1. Алексеем (`athlete-a`) создать будущую встречу с режимом «По заявке». В карточке перейти по «Рассмотреть заявки».
2. Марией (`athlete-b`) нажать «Подать заявку». Проверить «Ожидает решения», отсутствие себя в участниках и нулевой подтверждённый счётчик. Reload не теряет заявку.
3. Ириной (`athlete-c`) также подать заявку.
4. Организатором открыть карточку: в «Заявки на участие» есть оба человека. Одобрить Марию, отклонить Ирину, при желании указать причину. Проверить фильтры «Одобренные» и «Отклонённые».
5. Мария видит «Вы участвуете» / «Заявка одобрена», Ирина — «Заявка отклонена» и причину. При открытии в двух независимых браузерных профилях активная страница PENDING обновляется в течение очередного 5-секундного polling. В одном профиле переключение аккаунта меняет общую cookie-сессию.
6. Перезагрузить страницы всех сторон: решения сохраняются. Подтверждённый счётчик и список участников включают только Марию. Повторная подача и повторное решение не создают дублей.

S4 на моках: тот же путь с user-alex → user-maria и admin как вторым заявителем. В полном браузерном прогоне проверены обе ветви и все пять ширин 320/375/768/1024/1440. На Java — два независимых BrowserContext, обе ветви и обновление без reload, затем сохранение после reload на 375/768/1440. В Java-прогоне дополнительно проверено: ADMIN читает список (200), но не может решить чужую заявку (403). Скриншоты desktop/mobile просмотрены визуально.

В unit/API проверены PENDING без резервирования мест, отказ при заполненном составе, EVENT_FULL при одобрении с сохранением PENDING, гость/CSRF/чужой организатор/ADMIN, неверные payload, повторное решение и начало события, фильтры/пагинация, disabled во время запроса, retry и отсутствие ложного успеха, фокус формы отказа, чужой ответ и поздний ответ после смены аккаунта. Новая подача APPROVAL принимает только ответ PENDING, не ошибочное немедленное подтверждение.

## S5: обсуждение без записи

1. Алексеем (`athlete-a`) создать опубликованную встречу. Марией (`athlete-b`) открыть её, не подавая заявку и не записываясь.
2. В «Обсуждение встречи» задать вопрос. После отправки появятся автор, время UTC и текст; поле очистится. Кнопка записи по-прежнему доступна, число участников не меняется.
3. В отдельном браузерном профиле организатором прочитать вопрос и отправить ответ. Личная отметка «Организатор» соответствует автору события.
4. Оставить обе страницы открытыми: новые сообщения приходят с очередным 10-секундным polling. Можно нажать «Обновить обсуждение». Reload обеих сторон сохраняет переписку.
5. Открыть ссылку в гостевом профиле: переписка видна, вместо формы — «Войти и написать». После входа возвращаемся к обсуждению этой встречи.
6. Проверить пустой/пробельный текст, ограничение 2000 символов и временную ошибку отправки: текст не теряется, ложного успеха нет. На длинном обсуждении работает пагинация и переход к последней странице после публикации.

На моках полный вопрос/ответ и reload проверены на 320/375/768/1024/1440, отдельно — возврат после входа. На Java — три независимых BrowserContext (организатор, незаписанный пользователь, гость), обновление без reload у обеих сторон, сохранение, публичное чтение, 404 отсутствующей регистрации, 403 без CSRF и 400 на пустой/слишком длинный текст на 375/768/1440. Service workers заблокированы, POST проверен как 201 без service worker. Мобильные и широкие скриншоты просмотрены.

Unit/RTL дополнительно проверяют trim, максимум 2000, неверный event/author/status/text в ответе, malformed DTO и даты без пояса, скрытие содержимого HIDDEN на границе, ошибки 401/403/404/409/422/503/сети, отмену запроса, поздний ответ после смены аккаунта, pending без дубля, HTML как текст, сохранение черновика при ошибке списка/отправки, retry, закрытую форму и пагинацию. Модерация отдельного комментария дополнительно проверяется сценарием S6 ниже.

## S2: заявка, допуск и публикация организации

1. Войти обычным аккаунтом, например тренером (`coach`), открыть `/organization`. Создать две разные заявки: имя, описание, необязательные виды спорта. У обеих статус «Заявка на рассмотрении», публикация от их имени недоступна. Личные события доступны независимо от заявки.
2. В отдельном профиле браузера войти администратором. На `/admin` найти заявки по названию/описанию. Одну одобрить, другую отклонить с причиной. Пустая причина не отправляется; при ошибке текст сохранён. Фильтры показывают оба итога.
3. Оставить кабинет представителя открытым: с очередным 10-секундным polling появляются оба результата, причина отказа и ссылка создания для одобренной организации. Обновление Session приходит с сервера; повторный вход не нужен.
4. После одобрения создать встречу по ссылке организации. В форме «Организатор встречи» уже выбрана нужная организация; можно создать личную встречу явным выбором. Успех — только после 201. Перейти по названию организатора из встречи в профиль.
5. Создать вторую встречу этой организации: нового административного согласования нет. Гостем открыть `/organizations`, найти клуб, открыть публичный профиль и обе встречи. Неодобренные/отклонённые заявки не появляются в каталоге и недоступны посторонним по прямой ссылке.
6. Перезагрузить кабинеты и профиль: решения, причина и встречи сохранены. Проверить отсутствие overflow, клавиатурный фокус формы отказа, поиск/фильтры/пагинацию и ошибки с retry.

На моках полный S2 пройден на 320/375/768/1024/1440, включая обе ветви, обязательную причину, сохранение, две публикации и видимость другому USER. На 320 проверено длинное неразрывное название. Отдельно проверены гостевой вход с возвратом к заявке и неправильный UUID. На Java — независимые представитель/ADMIN/гость, оба решения без reload представителя, повторное чтение после reload, 403/ORGANIZATION_NOT_APPROVED до одобрения, запрет публикации отклонённой организации, запрет admin-list для USER, 404 закрытой заявки гостю, две публикации без премодерации, реальный POST без service worker и публичная страница с событиями на 375/768/1440. Desktop/mobile скриншоты просмотрены.

Unit/RTL дополнительно покрывают границы длины, повреждённые DTO, неожиданные статусы/автора/результаты, приватность own-list, CSRF, повторное решение 409, отсутствие причины и статусы, пагинацию/admin-поиск, Abort, ошибки сети/сервера, сохранение полей после ошибки и запрет двойной отправки. Позднее решение другой сессии не объявляется успешным. Фоновая ошибка own-list не стирает черновик встречи. Запрос приватного профиля ждёт восстановления Session: отдельный тест с задержанной сессией подтверждает отсутствие ответа в гостевом кэше.

## S6: модерация и доступ заинтересованных

1. Под USER создать опубликованную встречу, другим USER записаться OPEN и задать вопрос. Организатором ответить. Администратор читает организатора, описание и обсуждение.
2. ADMIN на `/admin?section=events` ищет встречу по названию/описанию и переходит по «Комментарии мероприятия». Скрывает один комментарий с причиной 3–1000 символов и явным подтверждением. Пустая причина блокирует отправку, отмена возвращает фокус. Другие сообщения остаются, мероприятие ещё опубликовано. В админке скрытый текст доступен с меткой, обычным пользователям — нет.
3. ADMIN снимает событие с публикации с причиной. В фильтре «Снятые с публикации» видны новый статус и причина. Повторное действие возвращает 409, дубликатов нет.
4. В независимых сессиях участника/организатора открытая карточка обновляется очередным 10-секундным polling. Видны снятие и причина, прежняя запись сохранена, новые сообщения/запись закрыты. Reload сохраняет результат.
5. Посторонним/гостем проверить каталог и прямую ссылку: события нет в выдаче, детали дают 404. Прямой POST записи от вошедшего постороннего возвращает 409/EVENT_NOT_AVAILABLE. Участник продолжает читать карточку и оставшиеся сообщения.

На моках полный S6 пройден на 320/375/768/1024/1440. На Java — четыре независимых BrowserContext (организатор, участник, ADMIN, гость/посторонний), скрытие одного сообщения без удаления ответа, автоматическое закрытие без reload, прежний CONFIRMED после reload, причины снятия, отсутствие в каталоге, 404 прямого доступа и 409 новой записи на 375/768/1440. POST-модерации проверены как 200 без service worker; дополнительно проверены 403 для USER/без CSRF, 400 пустой причины и 409 повторного действия. Предусловие события S6 создаётся через публичный API, создание через форму отдельно покрыто S1. Desktop/mobile скриншоты просмотрены.

Unit/RTL проверяют границы причины (включая 1000/1001), неверный id/статус/причину/родительское событие в ответе, malformed DTO/пагинацию, все классы HTTP-ошибок и Abort, ADMIN/CSRF/валидацию без UI, сохранение остальных комментариев/регистраций, поиск/статусы/пагинацию, pending без дублей, retry с сохранённой причиной, фокус/отмену и поздний ответ после смены аккаунта. Отдельно проверены восстановление Session до приватного чтения и сохранение черновика при ошибке фонового polling.

Для сброса удалить эти ключи localStorage текущего origin и обновить страницу. Старые ключи событий/регистраций v1 игнорируются, автоматически не удаляются. В PostgreSQL эти действия ничего не меняют. Повреждённое хранилище даёт ошибку запроса, а не ложный успех.

## Не проверено и ограничения

- Показ автору причины скрытия комментария требует изменения контракта: текущий DTO/список не дают этих данных. Отмена и лист ожидания пока доступны только для чтения статуса; полного пользовательского пути для них нет.
- Firefox/Safari, физические устройства, screen reader и полный WCAG/контрастный аудит.
- Production hosting, HTTPS/cross-site cookies, несколько экземпляров Java и нагрузка.
- Конкурентные запросы отдельных процессов в рамках frontend-прогона; mock localStorage не заменяет транзакционность сервера.
- Сборка сохраняет прежние предупреждения Rollup о PURE-комментариях Zod и chunk более 500 kB (около 609 kB / 187 kB gzip real; Leaflet загружается отдельным chunk около 157 kB / 46 kB gzip). Предупреждения не подавляются.
