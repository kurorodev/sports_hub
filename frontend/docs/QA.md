## Ручной путь на Java

1. Поднять Docker/OrbStack, Java и PostgreSQL; запустить `npm run dev`, открыть `http://localhost:5173`. Убедиться, что нет отметки о локальных моках.
2. На `/login` выбрать Алексея (`athlete-a`). Создать встречу, указать свой спорт, будущую дату, время с поясом, свободную запись и 2 места. Дождаться подтверждения публикации. Перезагрузить — запись сохранена.
3. Войти Марией (`athlete-b`), найти встречу по названию либо новому спорту. Открыть и нажать «Присоединиться». Должны появиться «Вы участвуете», 1 из 2 и Мария в «Кто идёт». Перезагрузить и проверить статус в каталоге.
4. Переключиться на Алексея: он видит Марию, актуальное число участников и свою отметку организатора. Кнопка записи ему не предлагается.
5. Войти Ириной (`athlete-c`) и занять второе место. Представитель клуба (`org-approved`) увидит заполненную встречу. Повторная запись не создаёт дубликат.
6. Под администратором (`admin`) открыть `/admin`, затем под обычным пользователем проверить запрет. Кабинет пока каркас; модерация из него недоступна.
7. Проверить поиск, спорт, уровень, даты (UTC), пустую выдачу и сброс. Открыть `/events/not-a-uuid` для not-found. Проверить клавиатуру, видимый фокус, 375/768/1440 px и отсутствие общего горизонтального скролла.

На Java время из введённого offset возвращается в UTC: например, 18:30 UTC+07 — это 11:30 UTC. Пояс подписан возле времени; момент события сохраняется.

## Что доказал реальный браузерный прогон

S1/S3 на 375/768/1440: вход через UI → HttpOnly SPORT_SESSION → личное создание с произвольным новым спортом → 201 и правильный момент времени → reload → другой аккаунт находит событие → 404 собственной записи является нормальным отсутствием → POST без CSRF отклонён → UI с правильным CSRF получает 201/CONFIRMED → статус/численность/PublicUser обновлены → reload сохраняет участие → повторный POST возвращает 409 → организатор видит участника → другой пользователь заполняет второе место → следующий аккаунт видит отсутствие мест. Также проверены доступ ADMIN и очистка прав при переключении на USER.

Service workers в этом прогоне заблокированы, ответы создания и записи проверяются как полученные без service worker. Это запросы к Java, а не к MSW. Данные хранятся в PostgreSQL Docker volume. Подключение использует Vite proxy, поэтому независимое production-развёртывание этим не подтверждено. Реальные desktop/mobile скриншоты просмотрены визуально.

## S4: ручной путь на Java

1. Алексеем (`athlete-a`) создать будущую встречу с режимом «По заявке». В карточке перейти по «Рассмотреть заявки».
2. Марией (`athlete-b`) нажать «Подать заявку». Проверить «Ожидает решения», отсутствие себя в участниках и нулевой подтверждённый счётчик. Reload не теряет заявку.
3. Ириной (`athlete-c`) также подать заявку.
4. Организатором открыть карточку: в «Заявки на участие» есть оба человека. Одобрить Марию, отклонить Ирину, при желании указать причину. Проверить фильтры «Одобренные» и «Отклонённые».
5. Мария видит «Вы участвуете» / «Заявка одобрена», Ирина — «Заявка отклонена» и причину. При открытии в двух независимых браузерных профилях активная страница PENDING обновляется в течение очередного 5-секундного polling. В одном профиле переключение аккаунта меняет общую cookie-сессию.
6. Перезагрузить страницы всех сторон: решения сохраняются. Подтверждённый счётчик и список участников включают только Марию. Повторная подача и повторное решение не создают дублей.

S4 на моках: тот же путь с user-alex → user-maria и admin как вторым заявителем. В полном браузерном прогоне проверены обе ветви и все пять ширин 320/375/768/1024/1440. На Java — два независимых BrowserContext, обе ветви и обновление без reload, затем сохранение после reload на 375/768/1440. В Java-прогоне дополнительно проверено: ADMIN читает список (200), но не может решить чужую заявку (403). Скриншоты desktop/mobile просмотрены визуально.

В unit/API проверены PENDING без резервирования мест, отказ при заполненном составе, EVENT_FULL при одобрении с сохранением PENDING, гость/CSRF/чужой организатор/ADMIN, неверные payload, повторное решение и начало события, фильтры/пагинация, disabled во время запроса, retry и отсутствие ложного успеха, фокус формы отказа, чужой ответ и поздний ответ после смены аккаунта. Новая подача APPROVAL принимает только ответ PENDING, не ошибочное немедленное подтверждение.

## Моки и автоматическая регрессия

`npm run dev:mock`: Александр (`user-alex`) → создание → Мария (`user-maria`) → запись → Александр видит участника. Кабинеты — `org-run` и `admin`. Аккаунты, seed и база отличаются от Java, wire types — из того же YAML.

88 unit/integration-проверка покрывает границы слоёв настоящим ESLint Linter; независимые use cases с внедрённым repository; HTTP/DTO mappings, повреждённые ответы и все статусы; ответ для чужого аккаунта/события и поздний ответ после смены сессии; Abort; GET session, credentials/CSRF; создание с вложенным sport и organizer; серверные ошибки полей details[]; валидацию, pending/retry и сохранение ввода; каталог, фильтры и преобразование дат в ISO UTC; unlimited-лимит; OPEN, дубли, вместимость, error/retry и пагинацию участников.

28 mock browser-сценариев: каталог, прямые URL, роли, сохранение сессии, создание своего спорта и запись между аккаунтами. Полные S1/S3 — на 375/768/1440; shell и форма/участники дополнительно на 320/1024. Проверены длинные строки, клавиатура и отсутствие общего overflow. Mock-часы зафиксированы на 19 октября 2026, seed не сдвигается автоматически.

Mock persistence: `dvizh.mock.events.v2`, `dvizh.mock.registrations.v2`, session `dvizh.mock.account`. Для сброса удалить эти ключи localStorage текущего origin и обновить страницу. Старые ключи v1 игнорируются, автоматически не удаляются. В PostgreSQL эти действия ничего не меняют. Повреждённое хранилище даёт ошибку запроса, а не ложный успех.

## Не проверено и ограничения

- UI S5 обсуждений, S2 допуска организаций и S6 модерации ещё не готов. Отмена и лист ожидания пока доступны только для чтения статуса; полного пользовательского пути для них нет.
- Firefox/Safari, физические устройства, screen reader и полный WCAG/контрастный аудит.
- Production hosting, HTTPS/cross-site cookies, несколько экземпляров Java и нагрузка.
- Конкурентные запросы отдельных процессов в рамках frontend-прогона; mock localStorage не заменяет транзакционность сервера.
- Сборка сохраняет прежние предупреждения Rollup о PURE-комментариях Zod и chunk более 500 kB (около 540 kB / 170 kB gzip real). Предупреждения не подавляются.
