## Красная GPS-стрелка · gps/distance

Текущее местоположение отмечено отдельной красной стрелкой; она обновляется без пересоздания маркера, использует общий поток геолокации с фильтром расстояния, не блокирует маркеры объектов и исчезает при сбросе/потере координат. Кнопка карты возвращает к текущей позиции без повторного запроса, если GPS уже включён.

Проверены production build (TypeScript), lint, **11/11 профильных Vitest**, **2/2 mock Chromium** на 375/1440 px: включение кнопкой карты, цвет, движение стрелки без перемещения камеры, единственный маркер и сброс. Unit-проверки дополнительно покрывают нулевые координаты, временную потерю/восстановление сигнала, игнорирование поздних обновлений после сброса и разовое определение позиции в отдельной карте. Скриншоты просмотрены; публичная подложка в браузерных проверках отключена намеренно. Ручная БД не менялась. Backend/API не изменены; полный тестовый набор и Safari/Firefox не запускались.

`fix/admin/support`: администратору доступна только очередь поддержки; FAQ, личный список и создание скрыты, прямое создание запрещено сервером. Прошли 13 целевых Vitest, 2 Java Chromium на 375/1440 px, lint/build/api:check. Детали и ограничения — в [документации поддержки](../../backend/docs/support.md#режим-администратора).

Слияние master в fix/admincomment: сохранены поддержка и фильтры комментариев. По запросу пользователя тесты при слиянии не запускались; результаты ниже относятся к предыдущим проверкам.

Ветка `fix/admincomment`: [фильтры комментариев администратора](../../backend/docs/admin-comment-filters.md) — пользователь и мероприятие, совместимые ограничения «последние 10» и «за 24 часа», сохранение в URL и сброс. Доработан интерфейс: выровненные поля, видимые подсказки с первой буквы, пояснение поиска только по @никнейму, клавиатура и отдельное снятие выбранных фильтров. ## Ограничения календарей

В создании встречи календарь начинается с сегодняшнего дня в выбранном часовом поясе места встречи. Ручной ввод прошедшей даты или времени блокирует публикацию с ошибкой у поля. В каталоге и на карте обе границы начинаются с сегодняшнего дня UTC; дата окончания не может предшествовать началу. Недопустимый ручной ввод не меняет активный фильтр и URL. Очистка границ разрешена. Лимиты обновляются при возвращении на вкладку и раз в минуту.

Регрессия: `npm test -- src/tests/date-range.test.tsx src/tests/create-event.test.tsx` и `npm run test:e2e -- e2e/date-filters.spec.ts e2e/create-event.spec.ts e2e/map-navigation.spec.ts --workers=2`. Браузерные сценарии дат работают на сетевых моках; изменение API не требуется.

## Ручной путь на Java

1. Поднять Docker/OrbStack, Java и PostgreSQL; запустить `npm run dev`, открыть `http://localhost:5173`. Убедиться, что нет отметки о локальных моках.
2. На `/login` выбрать Алексея (`athlete-a`). Создать встречу, указать свой спорт, будущую дату, время с поясом, свободную запись и 2 места. Дождаться подтверждения публикации. Перезагрузить — запись сохранена.
3. Войти Марией (`athlete-b`), найти встречу по названию либо новому спорту. Открыть и нажать «Присоединиться». Должны появиться «Вы участвуете», 1 из 2 и Мария в «Кто идёт». Перезагрузить и проверить статус в каталоге.
4. Переключиться на Алексея: он видит Марию, актуальное число участников и свою отметку организатора. Кнопка записи ему не предлагается.
5. Войти Ириной (`athlete-c`) и занять второе место. Представитель клуба (`org-approved`) увидит заполненную встречу. Повторная запись не создаёт дубликат.
6. Под администратором (`admin`) открыть `/admin`, затем под обычным пользователем проверить запрет. Кабинет рассматривает заявки организаций; модерация мероприятий/комментариев доступна в отдельных разделах.
7. Проверить поиск, спорт, уровень, даты (UTC), пустую выдачу и сброс. Открыть `/events/not-a-uuid` для not-found. Проверить клавиатуру, видимый фокус, 375/768/1440 px и отсутствие общего горизонтального скролла.

На Java время из введённого offset возвращается в UTC: например, 18:30 UTC+07 — это 11:30 UTC. Пояс подписан возле времени; момент события сохраняется.

## Что доказал реальный браузерный прогон

S1/S3 на 375/768/1440: вход через UI → HttpOnly SPORT_SESSION → личное создание с произвольным новым спортом → 201 и правильный момент времени → reload → другой аккаунт находит событие → 404 собственной записи является нормальным отсутствием → POST без CSRF отклонён → UI с правильным CSRF получает 201/CONFIRMED → статус/численность/PublicUser обновлены → reload сохраняет участие → повторный POST возвращает 409 → организатор видит участника → другой пользователь заполняет второе место → следующий аккаунт видит отсутствие мест. Также проверены доступ ADMIN и очистка прав при переключении на USER.

Service workers в этом прогоне заблокированы, ответы создания и записи проверяются как полученные без service worker. Это запросы к Java, а не к MSW. Данные хранятся в PostgreSQL Docker volume. Подключение использует Vite proxy, поэтому независимое production-развёртывание этим не подтверждено. Реальные desktop/mobile скриншоты просмотрены визуально.

## S4: ручной путь на Java

1. Алексеем (`athlete-a`) создать будущую встречу с режимом «По заявке». В блоке «Встречаемся здесь» без ожидающих заявок показана серая заблокированная кнопка «Новых заявок нет»; нажатие не прокручивает страницу. При появлении `PENDING` серверный счётчик обновляется при опросе (раз в 10 секунд), появляется жёлтая ссылка «Рассмотреть заявки» на список заявок. После последнего решения снова показана заблокированная кнопка, в том числе при просмотре одобренных и отклонённых заявок.
2. Марией (`athlete-b`) нажать «Подать заявку». Проверить «Ожидает решения», отсутствие себя в участниках и нулевой подтверждённый счётчик. Reload не теряет заявку.
3. Ириной (`athlete-c`) также подать заявку.
4. Организатором открыть карточку: в «Заявки на участие» есть оба человека. Одобрить Марию, отклонить Ирину, при желании указать причину. Проверить фильтры «Одобренные» и «Отклонённые».
5. Мария видит «Вы участвуете» / «Заявка одобрена», Ирина — «Заявка отклонена» и причину. При открытии в двух независимых браузерных профилях активная страница PENDING обновляется в течение очередного 5-секундного polling. В одном профиле переключение аккаунта меняет общую cookie-сессию.
6. Перезагрузить страницы всех сторон: решения сохраняются. Подтверждённый счётчик и список участников включают только Марию. Повторная подача и повторное решение не создают дублей.

S4 на моках: тот же путь с user-alex → user-maria и admin как вторым заявителем. В полном браузерном прогоне проверены обе ветви и все пять ширин 320/375/768/1024/1440. На Java — два независимых BrowserContext, обе ветви и обновление без reload, затем сохранение после reload на 375/768/1440. В Java-прогоне дополнительно проверено: ADMIN читает список (200), но не может решить чужую заявку (403). Скриншоты desktop/mobile просмотрены визуально.

В unit/API проверены PENDING без резервирования мест, отказ при заполненном составе, EVENT_FULL при одобрении с сохранением PENDING, гость/CSRF/чужой организатор/ADMIN, неверные payload, повторное решение и начало события, фильтры/пагинация, disabled во время запроса, retry и отсутствие ложного успеха, фокус формы отказа, чужой ответ и поздний ответ после смены аккаунта. ## Не проверено и ограничения

- Показ автору причины скрытия комментария требует изменения контракта: текущий DTO/список не дают этих данных. Отмена и лист ожидания пока доступны только для чтения статуса; полного пользовательского пути для них нет.
- Firefox/Safari, физические устройства, screen reader и полный WCAG/контрастный аудит.
- Production hosting, HTTPS/cross-site cookies, несколько экземпляров Java и нагрузка.
- Конкурентные запросы отдельных процессов в рамках frontend-прогона; mock localStorage не заменяет транзакционность сервера.
- Сборка сохраняет прежние предупреждения Rollup о PURE-комментариях Zod и chunk более 500 kB (около 609 kB / 187 kB gzip real; Leaflet загружается отдельным chunk около 157 kB / 46 kB gzip). Предупреждения не подавляются.

## Кнопка заявок в «Встречаемся здесь» · fix_event_window

Кнопка использует `pendingCount` из серверного `/events/{id}/team`, независимо от выбранного фильтра списка заявок. При `PENDING > 0` ссылка «Рассмотреть заявки» жёлтая; при нуле — серая нативная disabled-кнопка «Новых заявок нет» без якоря и прокрутки. Решения обновляют счётчик через существующую инвалидацию кэша, новые заявки из другой сессии — через 10-секундный опрос. Контракт и backend-бизнес-код не менялись.
