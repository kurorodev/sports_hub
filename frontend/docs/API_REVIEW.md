# API: интеграция и вопросы для ревью

Статус на 19 октября 2026: **API INTEGRATED / E2E VERIFIED для shell/session, каталога, S1–S6, профиля и регистрации демопользователя**. Проверено на Java 21 + Spring Boot + PostgreSQL через Docker. Это не статус всех серверных операций.

## Источники

Доступны [OpenAPI 1.0.0-draft](../../backend/contracts/openapi.yaml), [командная спецификация](../../backend/docs/TEAM_SPEC_DETAILED.md), исходные PDF в `backend/docs/source/` и [решения backend](../../backend/docs/decisions.md). Backend регистрации и обновлённый контракт объединены из `feature/demo-registration-20261019`. Финальное утверждение draft остаётся задачей команды; текущая интеграция использует его без добавления неподтверждённых DTO.

`npm run api:generate` создаёт `src/shared/api/generated/schema.d.ts`. `src/shared/api/types.ts` экспортирует aliases на generated types, а не ручные копии DTO. `npm run api:check` сверяет генерацию с YAML. Временные файлы provisional удалены. Ограничения UI-формы сверены с EventCreate: название 3–160, описание 10–5000, название активности в «Другое» 2–80, город до 120, адрес до 300, лимит формы 2–10000. Java независимо проверяет данные и права.

После переключения аккаунта очищаются query cache и состояние страницы. Успех показывается после ответа API. Изменение количества мест не вычисляется оптимистически в UI.

## Профили, условия участия и регистрация

`/profile` читает собственный профиль и позволяет редактировать поля из `UserProfilePatch`; `/users/:userId` показывает публичный профиль гостю. HTTP-адаптер проверяет DTO и идентификатор, обновление проходит через чистый use case. Ошибка nickname 409 сохраняет ввод; чужой профиль не предлагает редактирование. USER-организатор ведёт в профиль из каталога, деталей и админки; ORGANIZATION сохраняет переход к организации.

`EventCreate.requirements` — необязательный текст до 2000 символов. Форма отправляет trimmed-значение либо `null`; детали события выводят непустой текст с переносами обычными React-узлами. HTML не интерпретируется. Поле и лимит уже были в backend-контракте.

`/register` отправляет `DemoRegistrationRequest` `{nickname, displayName}` в `POST /demo/accounts`. UI обрезает внешние пробелы; nickname 3–40, displayName 1–100. Только 201 считается созданием: отдельный USER без административных прав, Session и новая HttpOnly-cookie. Запрос не повторяется автоматически. 400/422 показывают ошибки ввода, 409 — занятый nickname, 404 — недоступный деморежим; форма сохраняется. После успеха отменяются прежние запросы, очищается кэш и сохраняется CSRF. Вход и регистрация используют общий разрешённый возврат к профилю, созданию встречи, записи, обсуждению, карте или кабинету организации.

Новый аккаунт сохраняется в PostgreSQL и доступен в `GET /demo/accounts`; повторный вход использует его стабильный `DemoAccount.id` через `POST /demo/session`. Это демонстрационный вход без пароля; новый аккаунт доступен общему списку переключения. В mock mode отдельные новые аккаунты сохраняются в `dvizh.mock.accounts.v1`, правки профилей — в `dvizh.mock.profiles.v1`. Java-сессии остаются в памяти backend; после его перезапуска нужен повторный вход, сам пользователь сохраняется.

Для доступности записи используется уже реализованный `/team` (P1 по YAML), чтобы не изобретать временный registrationOpen и не определять бизнес-доступность по часам браузера. Участники и собственный статус остаются отдельными запросами. Чистое ядро S3 работает через repository port; DTO/HTTP преобразуются в адаптере. Все пять статусов регистрации отображаются корректно при чтении имеющихся серверных данных.

## S4: заявки и решения

Подключены `GET /events/{eventId}/registrations` со статусом и пагинацией и `POST /events/{eventId}/registrations/{registrationId}/decision`. UI отправляет APPROVE или REJECT; причина отказа необязательна, максимум 1000 символов по RegistrationDecisionRequest. Список и действия встроены в страницу APPROVAL-события только для viewerIsOrganizer. ADMIN имеет серверное право читать список, но не получает интерфейс решения чужих заявок; прямой POST от него возвращает 403.

Ожидающая заявка не занимает место, даже если подтверждённых уже достаточно: APPROVAL можно подать при заполненном лимите. При одобрении сервер повторно проверяет вместимость; EVENT_FULL оставляет заявку PENDING, отказ возможен и при полном составе. Повторное решение, чужая заявка или закрытое событие не дают ложного успеха. Реальная конкурентность обеспечивается Java/PostgreSQL, не клиентом.

Repository расширен операциями listRequests/decide; отдельный чистый use case reviewRegistration проверяет идентификаторы события, регистрации, участника и ответный статус. DTO и исходные поля не выходят в ядро. После решения обновляются запросы события, заявок и участников. Статус PENDING у заявителя проверяется HTTP polling раз в 5 секунд в активной странице; список организатора — раз в 10 секунд, также есть ручное обновление. При смене аккаунта поздний ответ не попадает в новую сессию.

## S5: публичное обсуждение

Подключены `GET /events/{eventId}/comments?page=&size=` (PagedComments) и `POST /events/{eventId}/comments` с CommentCreate `{text}` и ответом Comment (201). Чтение опубликованного события публичное; отправка требует сессию и CSRF, но не регистрацию. Публикация комментария не меняет заявки и число мест. Java проверяет статус события: новые сообщения только для PUBLISHED; дата начала не закрывает обсуждение автоматически.

Текст — от 1 до 2000 символов, пробельная строка недопустима. Java возвращает 400/VALIDATION_ERROR при ошибке валидации; моки повторяют это поведение. UI также распознаёт 422 как ошибку ввода. Пустая выдача — успешная страница с total=0, а 404 комментариев остаётся ошибкой доступа/отсутствия события. Список упорядочен сервером по createdAt и id, показано по 10 сообщений. Есть пагинация, ручное обновление и HTTP polling раз в 10 секунд в активной вкладке.

Публикация идёт через CommentRepository и чистый publishComment: ответ сверяется с событием, автором, текстом и статусом. Нет оптимистической вставки или автоматической повторной отправки. При ошибке ввод сохраняется; после 201 список перечитывается, открывается последняя страница. Гость после входа возвращается к якорю обсуждения. HTML показывается обычным текстом. HIDDEN преобразуется в модель без текста и отображается заглушкой, если сервер вернул скрытое сообщение администратору; для обычного пользователя Java исключает HIDDEN из списка.

Метка «Организатор» показывается только для личного организатора, когда Event.organizer.type=USER и id совпадает с Comment.author.id. Для организации автор — пользователь, а organizer.id — организация: подтверждённого признака представителя в Comment нет. Метка по имени или системной роли не угадывается. Модерационные действия подключены в S6; новые контракты не вводились.

## S2: организации и административный допуск

Подключены `POST /organizations`, `GET /me/organizations`, `GET /organizations?q=&page=&size=`, `GET /organizations/{id}`, `GET /organizations/{id}/events` и административные `GET /admin/organizations?q=&status=&page=&size=` / `POST /admin/organizations/{id}/decision`. Используются generated OrganizationCreate, Organization, PagedOrganizations и OrganizationDecisionRequest, без нового контракта.

Подать заявку может вошедший USER: Java назначает создателя представителем, а роль ORGANIZATION и manageableOrganizationIds вычисляет только по APPROVED. Это серверные полномочия, а не выбранный при входе тип интерфейса. Поэтому `/organization` доступен любому вошедшему, `/admin` — только ADMIN. В публичном каталоге только APPROVED; PENDING/REJECTED видны в деталях автору и администратору, постороннему Java возвращает 404. В UI есть поиск и пагинация, свои заявки и причина решения.

Форма ограничена именем 2–160, описанием 10–2000 и необязательным выбором спортов; avatarUrl интерфейс пока не предлагает. Отказ требует причину 3–1000 символов. Переходы только PENDING → APPROVED/REJECTED; повторное решение даёт 409. Unit/RTL проверяют pending без дублей, сохранение полей при ошибке и поздний ответ предыдущей сессии. Списки кабинета и администратора обновляются раз в 10 секунд на активной странице, есть ручное обновление. При изменении допуска перечитывается Session: права UI не назначает по статусу самостоятельно.

Создание встречи отправляет organizer `{type:ORGANIZATION,id}` вместо USER по явному выбору. Выбор ограничен одобренными собственными организациями и серверным manageableOrganizationIds. Прямой URL с pending/rejected/чужой организацией не открывает форму от её имени. Java независимо возвращает 403/ORGANIZATION_NOT_APPROVED до допуска, а после одобрения сразу публикует события без нового решения администратора. Карточки и детальная страница ведут на организацию; её встречи читаются отдельным endpoint. Ошибка фонового обновления организаций не уничтожает введённую форму встречи; сервер всё равно проверяет права при публикации.

На Java проверены обе ветви на разных заявках, получение решений в независимой сессии без reload, обновление роли/допуска, две последовательные публикации, публичное чтение и приватность неодобренных организаций. Описания, причины и статусы сохраняются в PostgreSQL. Редактирование организации и членство/чаты не входят в этот P0-срез.

## S6: модерация мероприятий и комментариев

Подключены `GET /admin/events?q=&status=&page=&size=` (PagedEventDetails), `POST /admin/events/{id}/unpublish` (Event), `GET /admin/comments?eventId=&page=&size=` (PagedComments) и `POST /admin/comments/{id}/hide` (Comment). Оба POST отправляют ModerationRequest `{reason}`: 3–1000 символов, CSRF и действующая ADMIN-сессия. Прежде отправки UI открывает форму с последствиями и явным подтверждением; при ошибке причина сохранена. Повторное действие над изменённым объектом даёт 409. Фильтр текста у комментариев не изобретался: API поддерживает только привязку к событию, доступную по ссылке из поиска мероприятий.

Решение назначает сервер. Чистый moderateContent проверяет id и целевой статус; для комментария — также eventId. Введённая причина проверяется перед отправкой и больше не ожидается в публичном Event DTO. Административные данные не выходят в гостевой кэш. После подтверждения перечитываются административные списки, затронутое обсуждение, события и регистрации. Никакого оптимистического скрытия всего обсуждения или клиентского изменения мест нет. Списки админки и активная карточка события обновляются HTTP polling раз в 10 секунд.

Java сохраняет существующие регистрации. UNPUBLISHED исчезает из каталога, а новая запись возвращает 409/EVENT_NOT_AVAILABLE даже по прямому API-пути. Организатор, ADMIN и пользователи с существующей регистрацией имеют прямой доступ; посторонний/гость получает 404. Причина снятия видна перед составом/записью, участникам поясняется сохранение прежнего статуса без обещания проведения встречи. Новые комментарии у неопубликованного события закрыты сервером.

HIDDEN исключается Java из публичного списка обычного пользователя; другие комментарии и событие остаются. Администратор получает исходный текст в `/admin/comments` и видит его только в защищённом разделе с явной меткой. Публичный CommentCard по-прежнему удаляет скрытый текст на API-границе. EventPage ждёт Session и использует viewerId в ключе чтения, чтобы приватный ответ при восстановлении cookie не оказался в гостевом кэше. Временный сбой polling не стирает черновик обсуждения; потеря доступа 401/403/404 закрывает данные.

**Закрыто 20.10.2026:** причина скрытия комментария доставляется автору через личные уведомления. Причина снятия события также перенесена в уведомления организатора. Публичная HIDDEN-заглушка с причиной не добавлялась; см. раздел «Личные уведомления» ниже.

## Время

На входе создаётся ISO-8601 с явно выбранным offset. Java хранит Instant и возвращает UTC `Z`: тот же момент может иметь другое отображаемое время. UI показывает пояс возле времени, обрабатывает и `Z`, и числовой offset. Обратное восстановление исходного городского пояса без отдельного поля контракта невозможно. Фильтры дат имеют явные границы UTC: начало дня `00:00:00Z`, конец `23:59:59.999Z`; это отмечено в интерфейсе.

## Что осталось для командного ревью

- OpenAPI описывает `q` как поиск по названию, описанию или спорту. Текущий `EventService.filters` ищет по названию/описанию; спорт фильтруется отдельным `sportId`/`sport`. Предлагаемое точечное решение — включить название спорта в серверный q либо уточнить описание общего контракта. Пока в поле поиска UI указаны название/описание, спорт выбирается отдельно.
- Конкретные исходные городские timezone не хранятся в Event. Для постоянного отображения местного времени города нужно согласовать отдельный IANA timezone либо политику отображения; текущая версия явно подписывает UTC/offset.
- Java допускает ручную запись организатора через API; UI не предлагает ему эту кнопку. Прежний mock-код ORGANIZER_CANNOT_JOIN удалён из HTTP mapping, не выдаётся за контрактный запрет.

## Границы

Основные сценарии S1–S6 подключены. Полная производственная готовность этим не подтверждена. Создание пока предлагает ACTIVITY; COMPETITION с endsAt и другие расширения будут отдельными задачами. Отмена и лист ожидания не реализованы в интерфейсе. `/admin` разделён на организации, мероприятия и комментарии; `/organization` показывает свои заявки и допуск.

Моки используют generated wire types, но остаются локальной эмуляцией: localStorage вместо БД и HttpOnly-cookie, собственные seed/аккаунты, без гарантии конкурентной записи независимых вкладок. События и регистрации используют `dvizh.mock.events.v2` / `dvizh.mock.registrations.v2` отдельно от прежних форматов v1; старые ключи не удаляются автоматически. Комментарии сохраняются в `dvizh.mock.comments.v1`, организации — в `dvizh.mock.organizations.v1`, причины/аудит модерации — в `dvizh.mock.moderation.v1`. Mock mode обозначен явно. Real mode не имеет fallback на MSW.

Проверки CORS, cookie, CSRF, создания, OPEN, APPROVAL с обеими ветвями, лимита, публичного обсуждения, допуска организаций и модерации пройдены в Chromium локально. Production hosting, несколько экземпляров Java, полноценная авторизация, Firefox/Safari и конкурентные запросы разных процессов в этом frontend-срезе не проверены.

## Карта: область фильтров каталога

`GET /map/events` принимает только bbox, sportId, from/to и limit. Переключение «Список / На карте» сохраняет остальные условия каталога для возврата, но явно объясняет, что они действуют только в списке. UI не отправляет неподдерживаемые параметры и не выдаёт выборку одной страницы `/events` за все события области. Для будущей эквивалентности режимов требуется совместно согласовать q, city, skillLevel, joinMode, eventKind, organizerType, hasSpots и политику includePast в контракте карты. Текущий UI работает без этих изменений; backend и OpenAPI в этой задаче не меняются.

Карта и её связь с записью/модерацией повторно проверены в объединённой версии: полный Java e2e 18/18, mock e2e 59/59. Поставщик адресных подсказок в Java-прогоне отключён; его успешный живой ответ этим прогоном не подтверждён.

## Замена библиотеки карты на MapLibre GL JS · 19.10.2026

Подключён MapLibre GL JS 6.15 с OpenFreeMap Liberty; ключ для подложки не нужен. Стиль можно заменить через `VITE_MAP_STYLE_URL` в `frontend/.env.local`. Worker библиотеки включён в сборку отдельным asset. Leaflet и react-leaflet удалены из зависимостей.

Сохранены ограничения `/map/events`, generated DTO, cookie/CSRF, серверные статусы и загруженность, календарные границы UTC и правила FSD. Условия списка, область `lat/lng/zoom`, слои, выбранный объект и возврат из встречи/входа продолжают передаваться через URL. Геокодирование остаётся через текущие `/geo/suggest` и `/geo/reverse`. Backend и OpenAPI для смены renderer не менялись. Выбор точки поддерживает мышь и стрелки клавиатуры; без WebGL доступен список вокруг заданного центра и повторная загрузка.

Живая подложка OpenFreeMap проверена в Chromium: стили, тайлы, подписи и атрибуция загрузились без ошибок JavaScript. Прежние результаты Java 18/18 выше относятся к версии до замены renderer; Java-прогон в этой задаче не повторялся. Успешный живой Geoapify по-прежнему не проверен без ключа.

## Обновление: парольный вход и упоминания · 19.10.2026

Текущий `/register` использует `POST /auth/register`, не прежний `/demo/accounts`. `/login` содержит форму `POST /auth/login` и отдельный демо-вход для старых аккаунтов. `/profile` позволяет завершить сессию (`DELETE /auth/session`, 204, cookie/CSRF). Общий транспорт корректно обрабатывает 204 без JSON. Созданные с паролем пользователи не имеют demoAccount и не доступны через демо-вход. После смены никнейма работают новый никнейм и прежний пароль. Точные ограничения, 400/401/409/429 и политика хранения описаны в [backend/passwords-and-mentions](../../backend/docs/passwords-and-mentions.md). Ранний раздел регистрации выше сохраняет описание демо-этапа.

`GET /users?nicknamePrefix=...` возвращает до 8 публичных пользователей. `Comment.mentions` и `Message.mentions` содержат стабильный userId, снимок nickname и диапазоны UTF-16. Клиент отправляет только text; ID и диапазоны разрешает сервер. В обсуждении есть подсказки, выбор стрелками/Enter, закрытие Escape и ссылки в тексте. Скрытые комментарии очищают и текст, и mentions на API-границе. Приватный доступ к беседам упоминания не меняют. UI личных/групповых бесед и уведомления этим обновлением не реализованы. Контракт содержит 62 операции; generated/runtime схемы обновлены совместно.

## Личные уведомления · 20.10.2026

По согласованию владельца продукта добавлены три операции `/me/notifications`, `/me/notifications/{notificationId}/read`, `/me/notifications/read-all`: всего 65 операций контракта. Backend хранит получателей и прочитанное; никакой подмены Java локальным состоянием нет. `NotificationPage.asOf` задаёт границу массового прочтения; unreadCount относится ко всему 30-дневному окну. Generated/runtime схемы согласованы.

Этот раздел заменяет прежние ограничения о недоступности причины скрытия комментария: автор получает её в личном уведомлении. Причина снятия события также только в уведомлении организатора; участники получают статус без причины. `Event.moderationReason` deprecated и null для всех, включая ADMIN.
