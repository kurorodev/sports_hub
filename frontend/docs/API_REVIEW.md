# Зависимости общего контракта

Статус: **временные модели моков, требуют командного ревью**.

В исходном checkout отсутствуют `contracts/openapi.yaml`, `docs/TEAM_SPEC_DETAILED.md`, `docs/source/case-brief.pdf` и `docs/source/scoring-criteria.pdf`. README в корне не содержит спецификации. Поэтому соответствие DTO и оценочной матрице пока не подтверждено. Корневые документы не менялись; `docs/DESIGN_SYSTEM.md` — локальная копия предоставленной системы v0.1.

## Реализованные срезы

P0-0: тема, layout, router, демо-вход, восстановление сессии и очистка кэша при смене аккаунта.
P0-1: каталог, фильтры, пагинация, просмотр события по прямому URL, empty/error/retry/not-found.
P0-2 / S1: создание личного события, новый вид спорта, сохранение между перезагрузками и сменой аккаунтов, видимость в каталоге второго пользователя.
P0-3 / S3: OPEN-регистрация → CONFIRMED, публичный список участников, актуальные счётчики/статус viewer, сохранение, запрет дублей и переполнения.

UI обращается через feature query/service → общий `request` → fetch. В mock mode запросы перехватывает MSW. UI не импортирует моки. Временные DTO находятся в `src/shared/api/provisional.ts`, а схема входа S1 — в `src/shared/api/provisional-event-schema.ts`. Они не считаются сгенерированным или утверждённым контрактом.

После архитектурного рефакторинга S3 проходит через `features/join-event/model` → `RegistrationRepository` → HTTP-адаптер в `entities/registration/api`. DTO проверяются и преобразуются в независимые модели, а HTTP-ошибки — в ошибки сценария. Сетевые пути и форматы mock API не изменены. Сессия и создание события пока используют прежние query/services. См. [ARCHITECTURE.md](ARCHITECTURE.md).

## Что нужно подтвердить с backend

| Endpoint                                        | Что сверить                                                                                                 |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GET /demo/accounts`                            | Массив или envelope, поля идентификатора и отображаемого имени                                              |
| `POST /demo/session`                            | `{accountId}`, форма Session, ответы ошибок                                                                 |
| `GET /session`                                  | `user`, системные роли, `manageableOrganizationIds`, CSRF, `demo`, 401 для гостя                            |
| `GET /events`                                   | Поля карточки, вложенные sport/location/organizer, capacity/confirmedCount, справочные enum и значения sort |
| `GET /events/{eventId}`                         | Детальный DTO, права viewer, 404/403, timezone                                                              |
| `GET /sports` (временный)                       | Массив `{id,name}`, жизненный цикл своих дисциплин, сортировка/пагинация                                    |
| `POST /events` (временный DTO)                  | `CreateEventInput`, валидация, ошибки полей, публикация, право автора, поддержка нового спорта              |
| `POST /events/{id}/registrations`               | Пустое тело, ответ Registration, 201 для OPEN, 409 для дубля/лимита                                         |
| `GET /events/{id}/my-registration`              | Ответ Registration, 404 при отсутствии, 401 для гостя                                                       |
| `GET /events/{id}/participants` (временный DTO) | Page<EventParticipant>, публичность, поля участника, порядок и пагинация                                    |

В моках используются временные строковые значения уровня и eventKind. Виды спорта загружаются через API, включая созданные. Фильтр города в каталоге пока содержит Москву и Санкт-Петербург; создать встречу можно в любом городе и найти её через спорт/поиск. `size` по умолчанию 6, `page` с нуля, `sort=startsAt,asc|desc` — временные решения. Доступные места и численность приходят из mock API, клиент не меняет их.

### Временное решение S1 для командного ревью

`src/shared/api/provisional-event-schema.ts` задаёт изолированную схему мока и общие ограничения UI/MSW. Новый спорт создаётся атомарно с событием через **один** `POST /events`: либо `sportId`, либо `customSportName`. Это не согласованный способ создания спорта на Java. Команде нужно определить отдельный endpoint или вложенное создание, DTO и обработку дублей.

Временные поля: `title` (3–120), `description` (20–3000), `sportId|customSportName` (новое название 2–60), `startsAt` (ISO с offset, строго в будущем), `location.{city,address}`, `skillLevel`, `eventKind`, `joinMode`, `capacity` (целое 2–1000). UI явно выбирает timezone из российских UTC+02…UTC+12; автоматического определения по городу нет. Границы, список timezone и enum требуют сверки с контрактом.

Mock API берёт автора из сессии, игнорирует присланные organizer/count/status, отвечает 201 с PUBLISHED, нулём подтверждённых участников и актуальным `viewerIsOrganizer`. Организатор не записывается автоматически. Совпадающие названия спорта нормализуются по регистру и пробелам. Ошибка 422 временно использует `ApiError.fieldErrors: Record<string,string>` с путями `location.city`, `startsAt` и т. п. Все эти решения подлежат совместному ревью.

### Временное решение S3 для командного ревью

Registration: `{id,eventId,user:{id,name},status:'CONFIRMED',createdAt}`. EventParticipant: `{user:{id,name},joinedAt}`. Участники временно публичны, ответ — `{items,page,size,total}`, `page` с 0, `size` UI 12 (mock максимум 50), новые записи первыми. Набор публичных полей и права просмотра должен подтвердить backend.

`POST /events/{id}/registrations` использует только сессию/CSRF, не доверяет присланным user/status. Mock проверяет событие, дубль (409 `ALREADY_REGISTERED`), организатора (403 `ORGANIZER_CANNOT_JOIN`), публикацию/время (409 `EVENT_NOT_AVAILABLE`), режим, вместимость (409 `EVENT_FULL`) и сохраняет одну CONFIRMED-запись. APPROVAL до S4 отвечает 501 `REGISTRATION_MODE_UNAVAILABLE`; UI не отправляет такой запрос. Это граница неполного mock API, не утверждённый ответ Java. Имена ErrorCode/HTTP-решения требуют сверки с общим контрактом.

`confirmedCount` вычисляется mock-сервером по CONFIRMED-регистрациям. Seed-счётчикам соответствуют синтетические участники. `viewerRegistrationStatus` возвращается из регистрации текущего пользователя. В EventPreview добавлен временный серверный `registrationOpen: boolean` (публикация + время), чтобы UI не назначал доступность записи по своим часам. Нужно подтвердить такое поле или эквивалент серверной доступности. Лимит и права всё равно повторно проверяются при POST.

Проверки и запись синхронны в одном JS-контексте мока; это не замена транзакции, уникальному ограничению и конкурентной защите на Java. Локальная база не гарантирует корректность одновременных записей из независимых вкладок/процессов. Настоящие конкурентные запросы на Java не проверялись.

## Границы текущего результата

- `/admin` и `/organization` проверяют сессию и показывают состояние доступа. Бизнес-операции кабинетов ещё не реализованы; наличие управляемой организации не означает её APPROVED-статус.
- Нет APPROVAL-заявок, решений организатора, обсуждений и модерации. Следующий срез — S4 APPROVAL. Отмена/лист ожидания пока отсутствуют.
- MSW сохраняет идентификатор тестового аккаунта под `dvizh.mock.account`, созданные события и дисциплины — в `dvizh.mock.events.v1`, регистрации — в `dvizh.mock.registrations.v1`. Это локальная база одного браузерного профиля/origin, а не общий сервер. Некорректное/недоступное хранилище приводит к ошибке запроса без скрытого сброса. `resetMockDatabase` сбрасывает события и регистрации в тестах.
- Mock-сессия эмулирует восстановление, не реализует HttpOnly-cookie. Настоящий `SPORT_SESSION` должен устанавливать Java backend; fetch уже использует `credentials: include`.
- POST создания и записи требуют сессию и корректный CSRF в MSW. Java обязан независимо валидировать payload и проверять права; клиентская схема этого не заменяет.
- Real mode не запускает MSW и не переключается на моки при ошибке. Реальная интеграция не проверена; одного изменения env недостаточно до подтверждения общего контракта.

После получения OpenAPI: запустить `npm run api:generate`, заменить импорты provisional на generated, сверить handlers, провести typecheck/tests и интеграционный e2e на Java. Не редактировать generated вручную.
