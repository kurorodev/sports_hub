# ДВИЖ · frontend

Реализованы P0 shell/session, каталог, S1 (личная встреча со своим видом спорта) и S3 (OPEN-запись и участники). React 19 + TypeScript strict + Vite 7, React Router 7, TanStack Query 5, Tailwind CSS 4 через Vite plugin, React Hook Form + Zod, MSW 2. Точные версии закреплены `package-lock.json`.

Работа на сетевых моках. **Java не интегрирован.** DTO временные: в checkout пока нет общего OpenAPI. Блокеры и границы: [API_REVIEW.md](docs/API_REVIEW.md). Исходная визуальная система: [DESIGN_SYSTEM.md](docs/DESIGN_SYSTEM.md).

## Запуск

Node.js 22.12+ или современная совместимая версия (разработка проверяется на Node 25), npm.

```sh
cd frontend
npm ci
npm run dev
```

Откройте URL из вывода Vite. `npm run dev` явно выбирает `.env.mock`. Вверху страницы видна отметка о моках; вся графика и Manrope поставляются локально. SVG-иллюстрации созданы для проекта, не выдаются за фото событий.

```sh
npm run dev:real
```

Этот режим выбирает `.env.real`. Относительный `/api/v1` проксируется Vite на `http://localhost:8080`. Java должен поддерживать согласованный контракт, cookie `SPORT_SESSION`, CSRF и демо-аккаунты. При другом origin настройте credentialed CORS, cookie SameSite/Secure и `VITE_API_BASE_URL`. UI не читает cookie. Backend требуется сверить с моделями перед подключением.

`.env.example` описывает переменные. Локальные overrides храните в игнорируемом `.env.local` или `.env.mock.local`/`.env.real.local`. `VITE_API_MODE` допускает только `mock|real`; по умолчанию real. `VITE_API_BASE_URL` — URL API без конечного `/`. Секретов здесь быть не должно.

```sh
npm run build         # production, real API, без запуска MSW
npm run build:mock    # явно выбранная демонстрационная сборка на моках
npm run preview      # просмотр последней сборки
```

При размещении SPA нужен fallback всех frontend-маршрутов на `index.html`, исключая `/api/*` и статические assets. Продакшен-сервер сам проксирует API; Vite dev proxy не входит в сборку. Публикация не выполнялась.

## Демо-аккаунты и ручной QA

На `/login` доступны Александр (`user-alex`), Мария (`user-maria`), представитель клуба (`org-run`) и администратор (`admin`). Организация определяется `manageableOrganizationIds`, а не выдуманной системной ролью ORGANIZATION.

1. Открыть каталог, выбрать спорт/город, найти событие. Фильтры сохраняются в URL после reload. Проверить пустую выдачу и сброс.
2. Открыть событие по ссылке. Дата показывает время исходного timezone-offset, без преобразования в часовой пояс браузера. Перейти на `/events/missing` для 404.
3. Войти администратором, перезагрузить, открыть `/admin`. Сменить аккаунт на Александра — ссылка «Модерация» исчезает, прямой `/admin` показывает запрет.
4. Войти представителем клуба и открыть `/organization`. Это только каркас доступа; одобрение организации ещё не реализовано.
5. Проверить 320/375/768/1024/1440 px и клавиатуру: видимый фокус, skip-link, поиск, фильтры, выбор аккаунта.

### S1: создатель → другой участник

1. Войти Александром, нажать «Создать» (`/events/new`). Для гостя доступен вход с возвратом к созданию.
2. Заполнить название, описание, выбрать «Свой вид спорта» и указать новую дисциплину, например «Алтимат». Можно выбрать существующий спорт.
3. Указать город, место, будущую дату, время и **часовой пояс места встречи** (для Красноярска UTC+07:00). Выбрать уровень, формат, число мест и OPEN/APPROVAL.
4. Нажать «Опубликовать встречу». После успешного ответа API откроется страница с подтверждением публикации и отметкой «Вы организатор». При ошибке значения формы сохраняются, можно повторить отправку.
5. Перезагрузить страницу — встреча сохраняется. Переключиться на Марию, выбрать новый спорт в каталоге или найти встречу поиском. Открыть её; отметка организатора Марии не показывается.

Все новые встречи пока **личные**. Публикация от имени организации появится в S2 после допуска; управляемая организация не даёт автоматически право такой публикации. OPEN-запись работает; подача APPROVAL-заявки — следующий срез.

### S3: OPEN-запись и участники

1. Александром создать будущую встречу со «Свободной записью» и лимитом 2 места.
2. Переключиться на Марию, открыть встречу и нажать «Присоединиться». После 201 от API появляется «Вы участвуете», счётчик становится 1 из 2, Мария появляется в «Кто идёт». Пока запрос pending, повторная отправка заблокирована.
3. Перезагрузить: подтверждение и участник сохраняются. В каталоге на карточке также виден статус участия.
4. Переключиться на Александра: в участниках есть Мария, число мест обновлено, организатор не записывается к себе.
5. Администратором занять второе место. Представитель клуба увидит, что все места заняты; повторную запись и переполнение блокирует mock API.
6. Гость может посмотреть список участников и войти с возвратом к событию. Отсутствие своей записи (`GET /my-registration` → 404) — обычное состояние, а не ошибка страницы. Сбой запроса предлагает retry; неподтверждённая операция не показывает успех.

Для быстрой проверки можно войти Марией и открыть `/events/morning-run`. Seed содержит 8 синтетических участников; после записи станет 9. APPROVAL и прошедшие встречи не получают работающую OPEN-кнопку. Уже подтверждённое участие сохраняется видимым после начала встречи. Отмена и лист ожидания пока не реализованы.

Seed содержит 6 демонстрационных событий 24 октября–1 ноября 2026 года. После этих дат включите «Показать прошедшие». Новые встречи и дисциплины сохраняются под `dvizh.mock.events.v1`, регистрации — под `dvizh.mock.registrations.v1` в localStorage текущего origin, отдельно от сессии `dvizh.mock.account`. Для полного сброса данных удалите оба первых ключа, для сброса входа — третий, затем обновите страницу. Seed восстановится автоматически. Аккаунты одного браузерного профиля видят общие события; на другом устройстве/в другом браузере эта локальная база не появится. Если хранилище недоступно или повреждено, запрос завершается ошибкой, а приложение не сообщает об успешной операции. Моки не используют персональные данные.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

RTL/Vitest проверяют фильтры, empty/error/retry, восстановление ролей, запрет доступа, HTTP/CSRF boundary, создание, ошибки полей, timezone, OPEN-запись, дубли и лимит мест. Playwright поднимает Vite в mock mode: каталог/прямые URL, переключение ролей, S1/S3 с перезагрузкой и адаптив. Браузерные скриншоты: `test-results/`, в git не входят. Автотесты не доказывают интеграцию с Java.

Архитектура: экраны собираются в `pages/`, действия — в `features/`, общие предметные модули — в `entities/`, инфраструктура — в `shared/`. Для S3 внедрены чистые модели, use cases, repository port, HTTP/DTO-адаптер и React-hook; конкретная реализация подключается в `app/providers.tsx`. Создание события и сессия пока используют прежние query/services. Правила направления импортов проверяются `npm run lint`. Подробная схема и границы перехода: [ARCHITECTURE.md](docs/ARCHITECTURE.md).

`JoinAction` находится в `features/join-event/ui`, карта отображения статуса — в `entities/registration/ui/presentation.ts`. Цвета, размеры и радиусы централизованы в `src/shared/styles/index.css`; CSS custom properties — источник темы, Tailwind 4 подключён через `@import 'tailwindcss'`.

Далее по AGENTS.md: S4 APPROVAL → S5 обсуждения → S2 организации → S6 модерация. P1/P2 пока не начаты. Формальный статус QA фиксируется в [QA.md](docs/QA.md).
